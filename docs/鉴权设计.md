# 鉴权设计:一套凭证、两种协议、连接生命周期

> 一句话结论:**系统用"一套凭证(token)+ 两种协议共用(TCP 握手 / HTTP)"鉴权——登录发 token,存 Redis `im:token:{token}=userId`;TCP 连接建立后第一帧必须是 HANDSHAKE,本地查 Redis 校验;HTTP 请求带 `Authorization: Bearer` 查同一个 key。** token 有效期 30 天,但只在握手/HTTP 请求时校验,过期不影响已建立的长连接。吊销 token 只挡"新握手",不踢"已建立连接"(纸面吊销,当前无 KICK 通道)。本文把鉴权从"凭证生成 → 两种协议入口 → 过期 → 吊销 → 踢下线 → 连接生命周期 → 攻击面"完整整理,含当前缺口与演进。

---

## 1. 凭证体系(三个身份,各司其职)

| 凭证 | 谁生成 | 作用 |
|---|---|---|
| **userId** | 服务端(注册分配) | 用户身份锚点,不变 |
| **deviceId** | 服务端(登录分配) | 设备身份,多端区分 |
| **token** | 服务端(登录生成) | 会话凭证,`im:token:{token} → userId`,TTL 30 天 |

**token 是"不透明随机串",不是签名 JWT**:服务端生成随机 token,存 Redis 做映射,校验 = 查 Redis,不验签名、无密钥管理。

```
登录 → 生成 token → SET im:token:{token} = userId (TTL 30天) → 返回 {token, deviceId, userId}
```

## 2. 两种协议的鉴权入口

| 协议 | 入口 | 校验方式 |
|---|---|---|
| **TCP 长连接**(实时收发) | 连接后**第一帧 HANDSHAKE**(body: token + deviceId) | connect 查 `im:token:{token}` → userId |
| **HTTP 接口**(拉历史/发消息/改头像等) | `Authorization: Bearer {token}` 头 | chat AuthInterceptor 查同一 key |

**同一份 token,一个来源(登录),两个消费方**——好处是一次登录两种通道都通,吊销在一个点生效。

## 3. TCP 握手鉴权细节

```
客户端 TCP 连上 connect 节点
  → 第一帧必须是 HANDSHAKE{token, deviceId}
  → HandshakeHandler.channelRead0:
      非 HANDSHAKE 帧 → ERROR(AUTH_REQUIRED) + 关连接      ← 第一帧强约束
      token/deviceId 缺 → ERROR(BAD_HANDSHAKE) + 关连接
      → sessionRegistry.authenticate(token) 查 Redis → userId
        userId 为空(无效 token)→ ERROR(AUTH_FAILED) + 关连接
        userId 有效 → register(userId, deviceId, nodeId)   ← 注册 Redis 会话表
                   → ChannelManager.add(本地) + ConnectionContext.bind
                   → 回 HANDSHAKE_ACK{userId}
                   → 移除 HandshakeHandler,后续帧交 MessageHandler
```

**关键点**:
- **鉴权在握手阶段,不是第一条业务消息**——未握手想发业务帧,直接关
- **校验 = 本地查共享 Redis**(`commands.get("im:token:"+token)`),不是验签名、不是发鉴权服务
- **握手成功后连接才进会话表 / 本地 ChannelManager**,身份锚定(ConnectionContext 绑定 userId/deviceId)

## 4. HTTP 鉴权细节

```
HTTP 请求 → AuthInterceptor(除 /api/auth/** 外全部拦截)
  → 取 Authorization: Bearer {token}
  → 查 Redis im:token:{token} → userId
  → 有效 → 写入 request attribute(AuthContext.currentUserId)
  → 无效 → 401
```

**越权防护**:业务接口一律从 `AuthContext.currentUserId(request)` 取当前用户,**不信任 URL 参数**——拉会话列表忽略传入 userId、拉消息校验会话归属、改头像只能改自己。这套在 AuthInterceptor + AuthContext 里实现。

## 5. token 过期策略(关键取舍)

**token TTL = 30 天**,但校验时机因协议而异:

| 协议 | 校验时机 | 过期后果 |
|---|---|---|
| **HTTP** | 每个请求都校验 | 过期立刻 401(重新登录拿新 token) |
| **TCP** | 只在握手那一刻校验 | **过期不影响已建立的长连接**(靠心跳续期会话,不查 token) |

**为什么 TCP 过期不影响已建连接**:连接的身份在握手时已锚定(ConnectionContext 绑定 userId/deviceId),后续收发不依赖 token;token 过期只该阻止"新的握手",不该打断"已建立的会话"。

**代价**:token 失效无法立刻吊销已建立连接——30 天 TTL + 断线重连重新校验兜底。

## 6. 吊销与踢下线(当前状态:纸面吊销,无 KICK)

### 现状(诚实)

```
吊销 token = 删除 Redis im:token:{token}
  → 新握手:authenticate 查不到 → 拒绝 ✓
  → 已建立的长连接:不受影响(靠心跳续期,不查 token)→ 继续活着 ✗
```

**当前吊销是"纸面吊销"**:挡住新握手,但**无法踢掉已建立的长连接**——没有 KICK 通道、没有周期性重新鉴权、没有"token 吊销 → 通知接入层踢连接"的机制。

### 要真吊销,需要"主动踢下线"两层配合

```
① 快路径 KICK:服务端发现 token 应吊销 → 查会话表定位节点 → 发 KICK 控制消息
   → 节点收到 → 本地 ChannelManager 找到连接 → close()
   (复用现有 MQ tag 路由基础设施,加一个 KICK 信封/控制 topic)
② 持久路径:吊销 = 删 token → 客户端重连握手失败 → 出局
   (节点死时也有效:连接已随节点死,KICK 到死节点无所谓,重连握手被拒才是关键)
```

**关键认知**:只关连接不够——客户端会自动重连,若 token 还有效会重新进来(白踢)。所以"踢下线 = 关连接 + 让重连失败"两个动作一起。

## 7. 连接生命周期(完整框架)

一条连接从生到死,每一步要定义"正常 + 失败"行为:

```
① 建连(accept)     正常:accept → 进握手;攻击:maxConnections 上限 + 限流;节点死:连接随进程死
② 握手鉴权         异步 Redis(不阻塞 EventLoop)+ 第一帧强约束 + 待鉴权超时 + 待鉴权限流
③ 会话建立         注册本地 ChannelManager + Redis 会话表(TTL 30s)
④ 保活             客户端 10s PING → 刷新会话 TTL;服务端 30s 读空闲 → 关死连接
⑤ 收发             上行 per-conversation 线程池;下行 EventLoop + isWritable 背压 + 拉取兜底
⑥ 踢下线           快路径(KICK)+ 持久路径(吊销 token 使重连被拒)——当前都没有
⑦ 吊销             删 token 挡新握手;踢活连接(KICK)当前缺失
⑧ 清理             断连清理本地 + 会话表;节点死靠会话 TTL 30s 自愈
```

## 8. 安全边界与攻击面

| 攻击 | 当前状态 | 防线/演进 |
|---|---|---|
| **空连接挂数千条** | 未握手一帧即关;已握手 30s 无心跳断 | ✅ 有(握手强约束 + IdleState) |
| **假登录灌爆握手** | 同步 Redis GET 阻塞 EventLoop(一次抖动卡全节点) | ⚠️ 要改:异步 Redis + 待鉴权超时/限流 |
| **token 被盗后建连接** | 纯 token 方案,拿 token 就能冒充 | ⚠️ 无解(行业常态);靠 HTTPS 难盗 + 短 TTL |
| **token 被盗后吊销** | 纸面吊销,已建连接不受影响 | ❌ 要补:KICK + 重连拒绝 |
| **偷 token 换设备用** | 无 deviceId 绑定校验 | ⚠️ 要补:握手校验 token↔deviceId 绑定 |
| **慢客户端拖垮节点** | isWritable 背压刚加 | ✅ L1 有了;L2-L4 演进(见慢客户端文档) |

## 9. 当前鉴权缺口清单(面试要能主动讲)

| 缺口 | 说明 |
|---|---|
| **握手同步阻塞 EventLoop** | authenticate 是同步 Redis GET,写在 channelRead0 → Redis 抖动卡全节点(最该改) |
| **吊销不踢活连接** | 纸面吊销,无 KICK 通道 |
| **无 deviceId 绑定** | 握手校验 token 但不校验"token 是否绑定该 deviceId" |
| **token 30 天偏长** | 被盗窗口大;演进短 token + 刷新 |
| **无单设备可选踢旧** | 多端并存,无"新登录踢旧设备" |

## 10. 面试问答

**Q: 为什么 token 过期不影响长连接?**
A: 连接身份在握手时已锚定(ConnectionContext 绑定 userId/deviceId),后续收发不依赖 token;token 过期只该阻止新握手,不该打断已建会话。代价是失效无法立刻吊销已建连接,靠 30 天 TTL + 重连重新校验兜底。

**Q: 怎么踢下线?**
A: 两层:快路径 KICK(查会话表 → 发控制消息到节点 → close 连接)+ 持久路径(删 token 使重连握手被拒)。只关连接不够——客户端会自动重连,必须同时让重连失败。当前两者都没实现。

**Q: token 被盗怎么办?**
A: 纯 token 方案拿 token 就能冒充,这是行业常态,靠"让 token 难盗"(HTTPS/短TTL/设备绑定)+"降低盗用影响"(可吊销)兜底,不靠"识别盗用者"。当前 token 30 天偏长,设备绑定没做,是已知缺口。

**Q: 握手鉴权阻塞吗?**
A: 当前是同步查 Redis,写在 EventLoop 上——Redis 抖动会卡全节点,这是设计原则("EventLoop 只做收发")的漏网之鱼,该改成异步 Redis。

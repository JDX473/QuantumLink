# 鉴权设计:一套凭证、两种协议、连接生命周期

> 一句话结论:**系统用"一套凭证(token)+ 两种协议共用(TCP 握手 / HTTP)"鉴权——登录发 token,存 Redis `im:token:{token}=userId`;TCP 连接建立后第一帧必须是 HANDSHAKE,本地查 Redis 校验;HTTP 请求带 `Authorization: Bearer` 查同一个 key。** token 有效期 30 天,但只在握手/HTTP 请求时校验,过期不影响已建立的长连接。吊销走 KICK(2026-08-09 已实现):删 token 挡新握手 + Redis Pub/Sub `im:kick` 广播踢掉已建连接。本文把鉴权从"凭证生成 → 两种协议入口 → 过期 → 吊销 → 踢下线 → 连接生命周期 → 攻击面"完整整理,含当前缺口与演进。

---

## 1. 凭证体系(三个身份,各司其职)

| 凭证 | 谁生成 | 作用 |
|---|---|---|
| **userId** | 服务端(注册分配) | 用户身份锚点,不变 |
| **deviceId** | **客户端**首启生成持久 UUID 存本地,服务端绑定账号 | 设备身份,多端区分;同一物理设备重装/重登不变 |
| **token** | 服务端(登录生成) | 会话凭证,`im:token:{token} → userId`,TTL 30 天 |

**token 是"不透明随机串",不是签名 JWT**:服务端生成随机 token,存 Redis 做映射,校验 = 查 Redis,不验签名、无密钥管理。

```
登录 → 生成 token → SET im:token:{token} = userId (TTL 30天) → 返回 {token, deviceId, userId}
```

## 2. 两种协议的鉴权入口

| 协议 | 入口 | 校验方式 |
|---|---|---|
| **TCP 长连接**(实时收发) | 连接后**第一帧 HANDSHAKE**(body: token + deviceId) | connect 查 `im:token:{token}` → userId |
| **HTTP 接口**(拉历史/发消息/改头像等) | `Authorization: Bearer {token}` 头 | chat AuthInterceptor 查同一 key |

**同一份 token,一个来源(登录),两个消费方**——好处是一次登录两种通道都通,吊销在一个点生效。

## 3. TCP 握手鉴权细节

```
客户端 TCP 连上 connect 节点
  → 第一帧必须是 HANDSHAKE{token, deviceId}
  → HandshakeHandler.channelRead0:
      非 HANDSHAKE 帧 → ERROR(AUTH_REQUIRED) + 关连接      ← 第一帧强约束
      token/deviceId 缺 → ERROR(BAD_HANDSHAKE) + 关连接
      → sessionRegistry.authenticate(token) 查 Redis → userId
        userId 为空(无效 token)→ ERROR(AUTH_FAILED) + 关连接
        userId 有效 → register(userId, deviceId, nodeId)   ← 注册 Redis 会话表
                   → ChannelManager.add(本地) + ConnectionContext.bind
                   → 回 HANDSHAKE_ACK{userId}
                   → 移除 HandshakeHandler,后续帧交 MessageHandler
```

**关键点**:
- **鉴权在握手阶段,不是第一条业务消息**——未握手想发业务帧,直接关
- **校验 = 本地查共享 Redis**(`commands.get("im:token:"+token)`),不是验签名、不是发鉴权服务
- **握手成功后连接才进会话表 / 本地 ChannelManager**,身份锚定(ConnectionContext 绑定 userId/deviceId)

## 4. HTTP 鉴权细节

```
HTTP 请求 → AuthInterceptor(除 /api/auth/** 外全部拦截)
  → 取 Authorization: Bearer {token}
  → 查 Redis im:token:{token} → userId
  → 有效 → 写入 request attribute(AuthContext.currentUserId)
  → 无效 → 401
```

**越权防护**:业务接口一律从 `AuthContext.currentUserId(request)` 取当前用户,**不信任 URL 参数**——拉会话列表忽略传入 userId、拉消息校验会话归属、改头像只能改自己。这套在 AuthInterceptor + AuthContext 里实现。

## 5. token 过期策略(关键取舍)

**token TTL = 30 天**,但校验时机因协议而异:

| 协议 | 校验时机 | 过期后果 |
|---|---|---|
| **HTTP** | 每个请求都校验 | 过期立刻 401(重新登录拿新 token) |
| **TCP** | 只在握手那一刻校验 | **过期不影响已建立的长连接**(靠心跳续期会话,不查 token) |

**为什么 TCP 过期不影响已建连接**:连接的身份在握手时已锚定(ConnectionContext 绑定 userId/deviceId),后续收发不依赖 token;token 过期只该阻止"新的握手",不该打断"已建立的会话"。

**代价**:token 失效无法立刻吊销已建立连接——30 天 TTL + 断线重连重新校验兜底。

## 6. 吊销与踢下线(2026-08-09 已实现)

### 机制:KICK = 删 token + Redis Pub/Sub 踢连接

```
吊销 token = 删除 Redis im:token:{token}
  → 新握手:authenticate 查不到 → 拒绝 ✓
  → 已建连接:chat 发布 KICK → connect 节点订阅 → 本地判目标关连接 ✓
```

**踢人四步**(chat 端发起):
① 删 token(踢死根基,重连握手必然失败)
② publish KICK 到 Redis Pub/Sub `im:kick` 频道({userId, deviceId})
③ 各 connect 节点 KickSubscriber 订阅广播,本地判目标(`ChannelManager.get != null` 才关)——只有持有连接者关,无连接节点零动作
④ connect 在目标 EventLoop 上 remove + close;close 触发 onDisconnect 清理 Redis 会话表

**为什么 KICK 走 Redis Pub/Sub 不走 MQ**:KICK 是控制信令,要求"全节点同时收到",Pub/Sub 天然广播、无消费者组概念(每个订阅者都收到),比 MQ 更贴合;即发即弃的缺点由"删 token 使重连被拒"兜底。

**持久路径兜底**:KICK 即发即弃——发布时不在线的节点会漏,但 token 已删,客户端被踢后重连握手必然失败 → 出局。**"删 token(让重连失败) + KICK(踢活连接)"两个动作一起才完整**:只关连接不删 token,客户端会无限重连进来(白踢)。

**两种触发**:
- **同端踢人(单设备模式)**:登录时 `AuthService.kickSameTypeDevices(userId, deviceType, excludeDeviceId)` 踢同 deviceType 的旧设备(删旧 token + publish KICK,排除正在登录的设备)
- **手动踢**:`POST /api/auth/devices/{deviceId}/kick`

**心跳修复(配套)**:HeartbeatHandler 续期前查会话表 `sessionRegistry.getNode`,路由表没了(被踢)→ 拒续期 + 关连接——否则被踢的死连接靠心跳续命,TTL 兜底失效。

**坑**:KickSubscriber 不能在 close 前 clear ConnectionContext——否则 onDisconnect 时 userId 为 null 提前返回,不清 Redis 会话表(会话残留,设备列表误判在线)。

## 7. 连接生命周期(完整框架)

一条连接从生到死,每一步要定义"正常 + 失败"行为:

```
① 建连(accept)     正常:accept → 进握手;攻击:maxConnections 上限 + 限流;节点死:连接随进程死
② 握手鉴权         **异步 Redis(已实现 2026-08-09:Lettuce async)** + 第一帧强约束 + 待鉴权队列(有界 64 帧)+ 待鉴权超时(3s)
③ 会话建立         注册本地 ChannelManager + Redis 会话表(TTL 30s)
④ 保活             客户端 10s PING → 刷新会话 TTL;服务端 30s 读空闲 → 关死连接
⑤ 收发             上行 per-conversation 线程池;下行 EventLoop + isWritable 背压 + 拉取兜底
⑥ 踢下线           快路径 KICK(Redis Pub/Sub 广播 + 本地判目标)+ 持久路径(删 token 使重连被拒)——已实现(2026-08-09)
⑦ 吊销             删 token 挡新握手 + KICK 踢活连接——已实现(2026-08-09)
⑧ 清理             断连清理本地 + 会话表;节点死靠会话 TTL 30s 自愈
```

## 8. 安全边界与攻击面

| 攻击 | 当前状态 | 防线/演进 |
|---|---|---|
| **空连接挂数千条** | 未握手一帧即关;已握手 30s 无心跳断 | ✅ 有(握手强约束 + IdleState) |
| **假登录灌爆握手** | **已异步**(2026-08-09):Lettuce async 不阻塞 EventLoop + 待鉴权队列限流(64 帧)+ 3s 超时 | ✅ 已修复 |
| **token 被盗后建连接** | 纯 token 方案,拿 token 就能冒充 | ⚠️ 无解(行业常态);靠 HTTPS 难盗 + 短 TTL |
| **token 被盗后吊销** | KICK 已实现:删 token 挡重连 + Redis Pub/Sub 踢活连接 | ✅ 已实现(2026-08-09) |
| **偷 token 换设备用** | 无 deviceId 绑定校验 | ⚠️ 要补:握手校验 token↔deviceId 绑定 |
| **慢客户端拖垮节点** | isWritable 背压刚加 | ✅ L1 有了;L2-L4 演进(见慢客户端文档) |

## 9. 当前鉴权缺口清单(面试要能主动讲)

> 2026-08-09 已关闭:**吊销不踢活连接**(KICK 已实现)、**无单设备踢旧**(同端登录踢旧设备)、**握手同步阻塞 EventLoop**(异步鉴权 + 待鉴权帧队列,见下)。剩余缺口:

| 缺口 | 说明 |
|---|---|
| **无 deviceId 绑定** | 握手校验 token 但不校验"token 是否绑定该 deviceId" |
| **token 30 天偏长** | 被盗窗口大;演进短 token + 刷新 |

## 10. 面试问答

**Q: 为什么 token 过期不影响长连接?**
A: 连接身份在握手时已锚定(ConnectionContext 绑定 userId/deviceId),后续收发不依赖 token;token 过期只该阻止新握手,不该打断已建会话。代价是"过期"本身不主动断连接——要立刻踢得显式走吊销(KICK);token 30 天偏长,靠重连重新校验兜底。

**Q: 怎么踢下线?**
A: 两层:快路径 KICK(删 token → Redis Pub/Sub `im:kick` 广播 → connect 节点本地判目标 close 连接)+ 持久路径(删 token 使重连握手被拒)。只关连接不够——客户端会自动重连,必须同时让重连失败。这套已实现(2026-08-09):同端登录踢旧设备、`POST /api/auth/devices/{deviceId}/kick` 手动踢。

**Q: token 被盗怎么办?**
A: 纯 token 方案拿 token 就能冒充,这是行业常态,靠"让 token 难盗"(HTTPS/短TTL/设备绑定)+"降低盗用影响"(可吊销)兜底,不靠"识别盗用者"。当前 token 30 天偏长,设备绑定没做,是已知缺口。

**Q: 握手鉴权阻塞吗?**
A: 已改成异步(2026-08-09):authenticate 走 Lettuce async,不阻塞 EventLoop;鉴权期间到达的业务帧入 per-connection 待鉴权队列(有界 64 帧 + 3s 超时),成功后按序补处理。之前同步版是"EventLoop 只做收发"的漏网之鱼——Redis 抖动会卡全节点,那是已修复的 🔴 bug。

**Q: 换成 JWT 是不是就不用和 Redis 交互了?**
A: 只能省"验证"那一步——JWT 本地验签就能确认 token 有效、解出 userId,不查 Redis。但 JWT 有个硬伤:**签了就无法撤销**。我的系统需要吊销(token 被盗踢下线)、踢旧设备、感知会话存活,这些都是状态管理,JWT 做不到,必须靠 Redis 黑名单或会话表——所以换 JWT 只是把 Redis 交互从"每次验证查"挪到"吊销时查黑名单",**并没有真正省掉 Redis**。IM 这类要吊销/会话状态的场景,纯 JWT 反而有硬伤,业界用"短期 JWT + 黑名单"混合。

**Q: 那纯 token(不透明随机串 + Redis)有什么问题?**
A: 四个:① 每次验证一次 Redis(性能,可解:Redis O(1) 或本地缓存);② Redis 成鉴权单点(挂了验证全断,但 Redis 本就是核心依赖);③ 无法携带声明(userId 要查库才拿到);④ 每个会话占 Redis 内存(可接受:几十字节 × 活跃用户)。但它换来的好处是**吊销天然支持**(删 key 即失效)、**不可伪造**(随机串靠 Redis 存在性)。本质是"有状态(可吊销) vs 无状态(省验证)"——IM 要吊销,纯 token + Redis 更合适;该补的是握手验证异步化 + 短期 token 缩小被盗窗口,不是换 JWT。

| 维度 | 纯 token(当前) | JWT |
|---|---|---|
| 验证 | 查 Redis(有状态) | 本地验签(无状态) |
| 吊销/踢下线 | ✅ 删 key 天然支持 | ❌ 无法撤销,靠黑名单(又查 Redis) |
| Redis 依赖 | 验证就依赖 | 吊销才依赖(黑名单) |
| 数据量 | 每会话占 Redis 内存 | token 无状态,Redis 只存黑名单(少) |
| 伪造风险 | 不可伪造(随机串+存在性) | 可伪造(密钥泄露) |
| 声明携带 | 不能(只当钥匙) | 能(userId/角色塞 token) |

# 设计审计 2026-08:当前 IM 还有什么漏洞

> 日期:2026-08-14。背景:下行发件箱(outbox)落地后,主动对全系统做一次**安全面 + 可靠性面**双线审计——每条结论落到 file:line 代码证据,不凭印象;外带会话清理链补查。

## 三、🔴 安全侧:三个可主动攻击的洞

### A1 群管理接口零授权:任何登录用户可拉人/踢人

**证据**:`GroupController.addMember(:76-89)` 与 `removeMember(:92-98)` 不做任何调用者校验——拉人不需要对方同意;踢人连 userId 都不从鉴权上下文取。任何登录用户可把任何人拉进任意群、踢掉群主或全体成员。groupId 获取难度极低:面对面建群是 4 位数字码(`GroupService.java:76`,5 分钟 TTL),可枚举。

**连带**:通过 self-add 先把自己拉进群,绕过拉取侧 isMember 门禁(`GroupController.java:127`)偷看任意群历史。

**修复方向**:addMember/removeMember 加调用者身份校验(踢人至少"我是群主或在退自己");拉人改成邀请制(对方同意)或产品层限制。

### A2 跨会话消息注入:conversationId 客户端可控 + 单聊无归属校验

**证据**:`MessageDispatcher.java:96-100` 只在 conversationId 为空时才由服务端计算,客户端自带的直接采用;`MessageService` 单聊路径(`:87-89` 及 asyncProcess)不校验"发送者必须是会话参与者"。攻击者发 MSG 时把 conversationId 设成 `B#C`、receiverId 设成 B 或 C → 消息落进 B、C 的私聊历史(sender 显示为攻击者),可定向投毒/钓鱼。**拉取侧的参与者校验只防读,不防写。**

**修复方向**:服务端一律重算 conversationId(单聊 = min#max);单聊校验 sender/receiver 一致性;群聊校验 isMember(A3)。

### A3 群消息发送无 isMember 校验:非成员可刷垃圾消息

**证据**:`MessageService.java:81-84` 凭客户端可控的 `g_` 前缀路由到群链路;`GroupService.handleGroupMessage`(:238 起)全程无成员校验——isMember 只存在于拉取侧(`GroupController.java:127`)。非成员向已知 groupId 刷消息,还污染群已读计数(`advanceGroupReadOnSend`)。

**A2+A3 同根**:信任了客户端的 conversationId。修法一致——MSG 帧只认 senderId(connect 盖章)+ receiverId,conversationId 由服务端推导(单聊 min#max、群聊校验成员后拼 `g_{gid}`)。

## 四、🔴 可靠性侧:三个丢消息窗口

### R1 取号后落库前崩溃:永久丢 + 重传被幂等键压 7 天(dedup 补落缺口实锤)

**窗口**:SETNX 过 + INCR 取号 → submit 线程池 → 落库前 kill -9。此时 MQ 位点已提交(`UpstreamConsumer.java:75-83` 返回 SUCCESS 即提交)、async 队列任务随进程消失(insert 在 `MessageService.java:140`,失败只打日志 :179-182)。客户端 6 次重传同 clientMsgId 全被 SETNX 挡(`:96-104` 判重后查无行 → 不发 ACK)→ 放弃并删 pending;pending 是内存 Map(`client-core.js:57`),客户端重启也清零。**唯一兜住条件:7 天内 Redis 也丢了 dedup key 且客户端还在重传窗口内——碰运气。**

此前文档记为"遗留缺口",本次审计确认它就是当前全系统最大的真实缺口。**修复方案已设计**:dedup 值存 seq(Lua GET+INCR+SET 一步),重复分支查无行时按原 seq 补落 + 重回 ACK。

### R2 seq 空洞无检测:位置一旦越过,漏掉的消息永久不可见

**窗口**:R1 的伴生(INCR 过未落库的号永不再用)+ 群消息在线漏推(背压跳过/MQ 丢)。客户端只有只进不退的 `conversationLastSeq`(`client-core.js:140-145`),收到 seq 跳变不补拉、重连只按 lastSeq 向后拉(`:291-296`)——位置越过后增量拉取够不到。**单聊靠 outbox 重推兜住了,群聊没有**;服务端 `serverMaxSeq` 取 DB max 也无法区分空洞("未落库"与"已丢失"同形)。

**修复方向**:客户端 gap 检测(收到 seq > last+1 → 拉 (last, seq) 区间),或服务端提供区间拉取/完整性校验接口。

### R3 群消息三重洞:无 outbox + 漏推不自愈 + 幂等重复分支无 ACK

1. **无 outbox**:读扩散无 per-member DELIVER 语义,群播 MQ 失败只打日志无重试(`DownstreamProducer.java:128-130`),在线成员漏推无任何补偿;
2. **漏推不自愈**:connect 背压跳过(`DownstreamConsumer.java:130-134`)后,客户端不重连就不补拉、重连也只从 lastSeq 拉——漏推后又有新群消息送达把 lastSeq 推过空洞,漏掉的那条永久丢失(同 R2);
3. **重复分支无 ACK**:群幂等重复分支直接 `return` 无回执(`GroupService.java:242-245`)——ACK 丢失时用户重传 6 次报"发送失败",手动重发新 clientMsgId → 群内真重复。单聊至少会查库补发原 seq ACK(`MessageService.java:99-102`),群没有。

**修复方向**:群 outbox(按 serverMsgId,不按 member)+ 重复分支补发原 seq ACK + 客户端 gap 检测(R2)。

## 六、🟢 低危(8 个)+ 会话清理链补查

1. **头像上传无内容校验、contentType 透传**(`AvatarStorageService.java:71-84`):上传 HTML 伪装头像,MinIO 按客户端 Content-Type 内联服务 → 存储型 XSS 面;`UserController.java:74` 全量 `file.getBytes()` 进内存。修:服务端校验魔数/重编码、固定 Content-Type。
2. **错误信息回显**(`AuthController.java:70-71`):`"register failed: " + e.getMessage()` 把 DB/MinIO 底层细节返回客户端;无全局异常处理器。修:统一异常处理。
3. **clientDeviceId 无长度/字符校验**(`AuthService.java:166-171`):超长 deviceId 进 Redis key 与 DB 列(device_id VARCHAR(64))→ 自我 DoS/登录 500。修:长度 + 字符集白名单。
4. **`/api/connects` 泄露节点拓扑**(`ConnectController.java:49-81`):任何登录用户可拿到全部 connect 节点 IP:port 与连接数。修:管理面或脱敏。
5. **schema 预置弱账号**(`schema.sql:123-125`):alice/bob `password_hash='dev-only'`,当前因格式不符无法登录,属生产隐患。修:生产构建移除种子数据。
6. **无 CORS 配置**:浏览器直连 API 场景需注意别引入宽松 CORS。
7. **`im:devices:{uid}` Set 无 TTL**(补查):正常断连有 SREM(`SessionRegistry.java:71-74` 清理链完整),但 connect 崩溃(kill -9)时 onDisconnect 不跑——session key 靠 30s TTL 过期,Set 里的 deviceId 永久残留。正确性无害(getOnlineNodes 逐个 GET 会跳过残留),长期泄漏。修:register 时给 Set 续 TTL,或定期清理无会话 key 的成员。
8. **register/remove 乱序理论竞态**(补查):同一 userId+deviceId 双连时,旧连接 remove 晚于新连接 register → `del` 删掉新会话,心跳只 expire 不重建 → 该设备永久路由不到直到重握手。deviceId 由客户端本地持久生成,同 deviceId 双连几乎不可能,理论面。

## 七、与既有记录的关系

**此前已知、本次升级/实锤**:

- dedup 补落缺口(遗留)→ 升级为 🔴 R1,确认是当前最大真实缺口;
- EventLoop 同步 Redis/MQ(CLAUDE.md 已知例外)→ 与代码一致(Y4);
- seq 计数器重启回绕(reconcile-seq.js)→ 拓宽到 **allkeys-lru 驱逐面**(Y2,新);
- im:devices 无 TTL(压测报告4 已发现)→ 补查确认清理链本身完整,残留只发生在进程崩溃场景。

**本次新发现**:A1/A2/A3(安全三高危)、Y3 雪花碰撞、Y1 背压计数误判、群幂等重复分支无 ACK(R3-③)、client-core 补拉只遍历本地已知会话(新会话首条消息在纯脚本客户端下不拉;桌面端靠 loadConversations + 打开时 pullTail 间接覆盖,风险限于测试客户端)、S1-S6。

**审计同时确认的"有防护"面**(无洞,面试可讲):拉历史/群历史的读侧越权有校验(AuthContext.isConversationParticipant、isMember)、改头像/踢设备有归属校验、READ_ACK 与 DELIVER_ACK 的 readerId/receiverId 由 connect 盖章、Netty 解码有 8MB 上限 + CRC、登录失败文案不区分用户不存在与密码错误(计时侧信道与 /api/users/resolve 枚举仍在 🟡)。

## 八、修复路线

| 优先级 | 项 | 理由 |
|---|---|---|
| **P0** | R1 dedup 补落(方案已设计,纯 chat 侧);A2+A3 服务端重算 conversationId + isMember(集中在 MessageService 入口,几处改动);R2 客户端 gap 检测(client-core 一处) | 消息正确性主线的最后一环 + 攻击面直接关闭;都是小改动 |

## 九、面试讲法

1. **主动审计本身是亮点**:交付后没有"写完就完",而是主动做双线审计——方法 = 每条结论落到 file:line 证据 + 按"可主动利用性 / 触发概率"分级(🔴🟡🟢),再排 P0/P1/P2 修复路线。这比"项目没有漏洞"可信得多,也比"有漏洞但说不清在哪"强得多。
2. **诚实讲已知未修**:Y4(EventLoop 同步调用)是权衡——心跳续期量级低、信令转发 3s 内,且握手鉴权已异步化作为改造示范;生产化项(S1-S4)是"知道业界标准做法、为什么这个项目没做"(秋招项目的合理边界)。
3. **把攻击面当设计题讲**:A2/A3 的根因一句话——"信了客户端的 conversationId",修法一句话——"只信 senderId(服务端盖章)+ receiverId,conversationId 服务端推导"。这种"根因一句话"是面试最值钱的部分。
4. **Y3 的诚实版本**:压测 13 万条没丢,不代表没撞——撞了会被幂等分支静默吞掉,"没丢"和"撞了没发现"在日志上不可区分;显式配置 workerId 之后这个盲区才关闭。能讲出"我压测通过但我仍不放心,查了 MP 源码找到 1/32 碰撞"是极强的加分项。

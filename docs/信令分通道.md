# 信令与消息分通道:队列级隔离

> 一句话结论:**MQ 上下行各拆独立信令 topic——消息走 `client2server`/`server2client`,信令(DELIVER_ACK/READ_ACK/ACK/DELIVER/READ/GROUP_READ)走 `client2signal`/`server2signal`,消息与信令队列级隔离,信令积压/重试不影响消息投递。**(2026-08-09)

## 动机

之前下行全混在 `server2client`:信令(ACK/已读)与消息(大 payload)要求不同,信令处理慢/重试会**队列级头阻塞**——前面一条信令卡住,后面所有消息都被拖住。分通道后,信令积压只拖信令,不碰消息。

## topic 布局(4 个)

| 方向 | 消息 | 信令 |
|---|---|---|
| 上行(connect → chat) | `client2server`(MSG) | `client2signal`(DELIVER_ACK/READ_ACK) |
| 下行(chat → connect) | `server2client`(MSG) | `server2signal`(ACK-STORE/DELIVER/READ/GROUP_READ) |

## 各侧实现

- **chat 上行消费**:DeliverAckConsumer / ReadAckConsumer **都订阅 `client2signal`**,靠字段区分——DELIVER 有 serverMsgId、READ 有 untilSeq,各自跳过对方
- **chat 下行生产**:`DownstreamProducer.topicFor(contentType)` 按信封类型分流——MSG → `server2client`,其余(ACK/DELIVER/READ/GROUP_READ)→ `server2signal`;配置在 application.yml `rocketmq.topics.downstream/signalDownstream`
- **connect 下行消费**:两个 `DownstreamConsumer` 实例分别消费 `server2client`(group 后缀 `-msg`)和 `server2signal`(后缀 `-signal`),group 名 `im-connect-consumer-{nodeId}-msg` / `-signal`
- **connect 上行发送**:消息走 `client2server`,信令由 `MessageDispatcher.dispatchDeliverAck/dispatchReadAck` 发到 `client2signal`

## 踩坑:topic 配置与实现不一致

- chat 的 DeliverAck/ReadAck 消费者**硬编码** `subscribe("client2signal","*")`,未用 `@Value` 读 yml → application.yml 的 `rocketmq.topics.signalUpstream` 是**死配置**,改 yml 不生效
- connect 侧全部 topic(`server2client`/`server2signal`/`client2server`/`client2signal`)**硬编码在代码**(NettyConnectServer / UpstreamProducer / MessageDispatcher),connect 无配置文件
- 两侧 topic 一致性靠**人工保证**——改一处要同步改另一侧 + yml

## 验证

单聊消息+已读、群已读、群已读实时推送(信令通道)、多端、多端踢人全链路回归通过;139 单测全过。

## 面试要点

- **为什么分通道**:信令(高频小消息)与消息(大 payload)混一条队列,信令积压/重试会头阻塞拖住消息投递;拆开后互不干扰,隔离单位是队列
- **怎么实现的**:topic 拆分 + 各侧按信封 type / 字段分流,消费者按 topic 独立消费
- **代价**:topic 变多,配置与代码不一致的风险(当前 connect 侧硬编码,诚实说明)
- **为什么 KICK 不走这套 MQ**:KICK 是 Redis Pub/Sub,见 [docs/多端踢人.md](docs/多端踢人.md)

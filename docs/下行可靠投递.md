# 下行可靠投递:服务端发件箱(未确认队列)+ 补拉对账回执

> 日期:2026-08-14。回答一个问题:**下行推送是"尽力而为"的,推丢了怎么办?**
> 结论:像微信/钉钉一样,服务端维护**未确认队列(发件箱)**,推过就入箱、收到接收方的 DELIVER_ACK 才出箱、超时未确认定时重推;客户端保持"傻"——收到回 ACK,其余判断全在服务端。
> 配套:单测 12 个(OutboxServiceTest)、验证脚本 scripts/verify-outbox.js(两场景实测 PASS)。

## 一、问题:下推到底哪里会丢

上行(客户端→服务端)有可靠锚点:落库 + ACK-STORE + 客户端超时重传 + 幂等去重,基本闭环。**下行的最后一跳(chat→MQ→connect→接收方 B)没有闭环**:

| 丢失点 | 现状(改前) | B 视角后果 |
|---|---|---|
| B 在线,MQ 投递/connect 消费环节丢 | 位点已提交,无重发 | **丢消息** |
| connect 侧背压跳过(`!isWritable`) | 位点提交,靠"补拉兜底" | 若 B 位置已越过该 seq → **丢消息** |
| B 收到推送,但 DELIVER_ACK 丢了 | 无重发 | A 永远看不到"已送达"(B 内容没丢,但状态错) |
| B 离线 | 不推,重连增量拉取 | ✅ 能补回(客户端 afterSeq 补拉) |

**为什么"补拉兜底"补不住在线丢推**:补拉只在重连时按位点 afterSeq 拉。B 收到了 seq=3 的消息、seq=2 的推送丢了 → B 位置=3,重连后 `afterSeq=3` 拉不到 2。**位置一旦越过丢失点,增量拉取就够不到了。** 这是核心死结。

**为什么不能简单"不提交 MQ 位点"**:RECONSUME_LATER 只覆盖消费异常;背压跳过/离线跳过是"业务决定"不是异常,commit 位点是必须的(否则一个坏消息卡死整个队列)。而且即便位点不提交,重投也只在进程内/位点层面,不可控。

## 二、业界标准答案:服务端未确认队列(outbox)

微信的 SYNC 协议、钉钉/飞书的同步机制,本质同一套模式:

```
发送方落库 → 下行推送(尽力而为) → 服务端记入【未确认队列】
接收方收到 → 回 DELIVER_ACK → 服务端出队 + 标记 DELIVERED → 通知发送方"已送达"
服务端定时扫描未确认队列 → 超时未确认且接收方在线 → 重推(指数退避)
接收方离线 → 不删不计数,等上线(上线补拉 + 补拉回执也能自然出队)
```

核心原则:**客户端笨、服务端聪明**。判断(推过没/确认没/超时没/在不在线/重推几次)全在服务端;客户端只做两件事:收到回 ACK、按 serverMsgId 去重渲染。重推是"至少一次"语义,靠幂等(serverMsgId 去重)转成"恰好一次"效果。

## 三、实现

### 3.1 数据结构(Redis,跨 chat 多实例共享)

```
im:push:outbox        zset:member=serverMsgId,score=下次检查时间(epoch ms)
im:push:outbox:meta   hash:field=serverMsgId,value="attempts,bornMs"
```

### 3.2 生命周期与各分支语义

```
入箱 add():推送真发出 MQ 后 ZADD(score=now+10s)+ HSET 元数据。
          接收方离线时本来就不推(补拉兜底)→ 不入箱。
          10s 首查窗口:正常消息 DELIVER_ACK 1s 内就回来出箱了,扫描器几乎看不见它。

出箱 remove():DELIVER_ACK 到达(实时推或补拉都算)→ ZREM+HDEL。不在箱里 = no-op。

扫描 scan()(@Scheduled 5s 一轮,ZPOPMIN 原子认领成员,处理完按新分数放回):
  ① 消息没了(被清理)→ 出箱
  ② DB 状态已 DELIVERED → 出箱(可能对方补拉后回了对账回执,无需重推)
  ③ 接收方离线 → 【不删、不计数】,30s 后复查
      关键:对方位置可能已越过此消息(收到了更新的),删了补拉也够不到 = 永久丢;
      必须保留到对方上线重推。若对方补拉后回 DELIVER_ACK,remove() 自然清掉。
  ④ 重推次数 ≥ 5 → 放弃 + ERROR 日志(避免死循环)
  ⑤ 入箱超 7 天 → 放弃 + ERROR 日志(接收方永久离线的兜底,与 dedup TTL 同窗口)
  ⑥ 在线 → 重推(按 DB 行重建 payload + 补发送者资料,走正常推送路径)
      成功后 attempts+1,按退避表重新 ZADD:30s / 1m / 2m / 5m / 5m
      MQ 发送失败 → 视同离线(30s 复查,不计数)
```

### 3.3 多实例安全

chat×2 各自跑扫描器。**ZPOPMIN 原子认领**:同一成员同一时刻只有一个实例弹走、处理、再放回——不会双发;另一个实例弹到的是别的成员(或空)。重推"至少一次"语义下客户端按 serverMsgId 去重渲染,即使真双发也无害。

### 3.4 补拉对账回执(客户端改动)

补拉回来的单聊消息也回 DELIVER_ACK(此前只有实时推送回)——离线漏推/位置越过场景靠它把消息标成已送达 + 发件箱出箱。群消息不回(读扩散无 per-member DELIVER 语义),顺手修掉了此前"群消息也回 DELIVER_ACK → chat 侧 warn 丢弃"的噪音。

### 3.5 防伪造(重要)

DELIVER_ACK 是"谁收到"的凭据,若发送方 A 伪造 B 的回执,消息会被提前出箱 + 误标已送达,**压掉对 B 的重推 = 制造丢消息**。防法:connect 转发 DELIVER_ACK 时已盖章 `receiverId = 连接认证用户`(MessageDispatcher.dispatchDeliverAck),chat 侧校验 `message.receiverId == ack.receiverId`,不符直接丢弃——回执必须来自真正的接收方连接。

### 3.6 范围边界

- **只覆盖单聊**:群消息读扩散(一份消息多接收方)、无 per-member DELIVER 语义,漏推靠补拉(群 seq 位点天然对齐,无单聊的"位置越过"死结——群成员位点是各自独立的)。
- **不覆盖 STORE 回执**:ACK-STORE 丢失靠客户端超时重传 + 幂等去重(既有机制)。
- **发送方视角的最终一致**:A 看到"已送达"最迟在重推窗口内(10s+退避);放弃兜底(5 次/7 天)后 A 永远看不到已送达——按"对账兜底"接受,日志 ERROR 可观测。

## 四、与"补拉兜底"的分工(面试讲法)

| 机制 | 覆盖 | 定位 |
|---|---|---|
| 发件箱重推 | 在线丢推(推送/回执丢失) | **主机制**(实时性:秒级~分钟级) |
| 重连补拉(afterSeq) | 离线期间的消息、慢客户端降级 | 对账机制(重连/上线时) |
| 补拉对账回执 | 补拉到的消息 → 标已送达 + 出箱 | 对账机制的回执,与发件箱共用 DELIVER_ACK 通道 |

一句话:**推送尽力而为,发件箱保证"推到了",补拉保证"补全了",两个机制共用同一条 DELIVER_ACK 出队路径。**

## 五、验证

- **单测**:OutboxServiceTest 12 个——入箱/出箱、空箱、未到期放回、已 DELIVERED 清理、消息消失清理、**离线保留不计数**、在线重推退避、MQ 失败不计数、次数上限放弃、年龄上限放弃、一轮多成员(到期处理/未到期放回)。`mvn test` 全过(im-chat 108)。
- **集成验证**:scripts/verify-outbox.js 两场景实测 PASS:
  1. **在线丢推 → 重推**:B(raw TCP)收推送不回 ACK → 服务端 ~10s 后重推同 serverMsgId(幂等)→ B 回 ACK → A 收到 DELIVER → 20s 内无第三次推送(出箱生效);
  2. **离线漏推 → 补拉对账**:B 离线时 A 发消息(不入箱)→ B 上线补拉 → 补拉回执把消息标已送达 → A 收到 DELIVER。

## 七、遗留与取舍

- **dedup 补落缺口(与发件箱正交,已设计未实现)**:SETNX 通过但 insert 前进程崩溃 → 重传被 dedup 键挡 7 天、消息静默丢。修复方案已设计:dedup 值存 seq(Lua GET+INCR+SET 一步),重复分支查无行时按原 seq 补落 + 重回 ACK。
- **重推窗口**:首次检查 10s + 退避(30s→5m),牺牲秒级时效换零丢失;真正要秒级可改成延迟 MQ 逐条定时(成本高,不值得)。
- **放弃兜底**:5 次/7 天上限是"对账兜底"的诚实边界,触发时 ERROR 日志可见,接受"极端情况下状态停在未送达"。

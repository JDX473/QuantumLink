# QuantumLink IM 压测报告(第一批)

> 日期:2026-08-05
> 压测工具:clients/loadtest/loadtest-throughput.js(复用 client-core.js 真实握手/心跳/重连)
> 环境:Windows 11 单机(压测机与被压系统同机,吞吐为保守值)

---

## 一、压测目标与方法

**目标**:验证消息链路(客户端 → connect → MQ → chat → 落库 → ACK 回)的吞吐、延迟与瓶颈位置。

**方法**:
- N 条 TCP 长连接两两配对互发消息,持续 T 秒
- 统计:发送量 / ACK 送达率 / 端到端延迟(发 → ACK-STORE 回)
- 每连接每秒固定消息数,逐步加连接数找到崩溃点

**架构**:2 个 connect(19001/19002)+ 1 个 chat + RocketMQ + Redis + MySQL,客户端轮流连两个节点(模拟跨节点)。

---

## 二、压测结果

| 连接数 | 吞吐 | 送达率 | P50 | P90 | P99 |
|--------|------|--------|-----|-----|-----|
| 10 | 19 条/秒 | 100% | 95ms | 219ms | 463ms |
| 50 | 146 条/秒 | 100% | 95ms | 219ms | 463ms |
| **100** | **290 条/秒** | **60.7%** | **6.1s** | **12.2s** | **14.2s** |
| 200 | 586 条/秒 | 40.1% | 12.2s | 21.2s | 24.4s |

**关键发现**:
1. **稳定水位:≤50 连接时链路可靠**(100% 送达,P99 463ms)
2. **崩溃点:50→100 连接之间**,延迟从 463ms 飙到 6 秒,送达率跌到 60%
3. **崩溃是"饱和型"不是"慢型"**:延迟随连接数线性恶化(100→200 连接,延迟翻倍)

---

## 三、瓶颈定位(已实锤)

### 瓶颈 1:connect 的 per-会话 executor 线程无限增长(主因)

**证据**:200 连接时 connect19001 进程 **439 个线程**,其中 **107 个 `conv-` 前缀的 per-会话 executor 线程**(每个会话一个单线程,永不回收)。

**根因**:`MessageDispatcher.conversationExecutors` 用 `computeIfAbsent` 为每个会话 new 一个单线程 executor,会话结束不回收。连接数上去,线程数线性增长 → 线程爆炸 → 系统饱和。

**为什么设计成这样**:为了保序(同一会话的消息串行 produce),但**"每会话一个线程"没有上限**——会话多时线程爆炸。

### 瓶颈 2(待验证):Redis keys 扫描

chat 发下行查会话表用 `redisTemplate.keys("im:session:{uid}:*")`——O(N) 全库扫描,阻塞单线程 Redis。群消息扩散时每个成员 keys 一次。压测中未单独隔离验证,但 100 连接时 Redis 出现 `RedisCommandTimeoutException`(1 分钟超时),与 keys 扫描阻塞相关。

---

## 四、数据可靠性验证

压测期间 **chat 落库 12256 条消息,0 失败、0 重复**(幂等双保险生效)。"未收到 ACK"是客户端 3s 超时重传(ACK 被慢链路拖到 >3s),消息本身全部落库成功——**链路不丢数据,只丢实时性**。

---

## 五、优化建议

### 修复 1(必做):per-会话 executor 改共享有界线程池 + hash 路由

```java
// 现状:每会话一个线程(无限增长)
conversationExecutors.computeIfAbsent(convId, k -> newSingleThreadExecutor());

// 修复:共享有界线程池(如 CPU×2),按会话 hash 路由到固定线程
// 同一会话 hash 到同一线程 → 保序不变;线程数有界不增长
int slot = convId.hashCode() % POOL_SIZE;
pool[slot].execute(() -> produce(...));
```

**预期**:线程数从"随会话增长"变成"固定 CPU×2",200+ 连接不再线程爆炸。

### 修复 2(建议):Redis keys 扫描改 Set 结构

每个用户一个 `im:devices:{uid}` Set 存设备,查在线直接 `SMEMBERS`,替代 `keys` 全库扫描。

---

## 六、结论

- **可靠性**:消息链路不丢不重(100% 落库),可靠投递设计成立
- **性能瓶颈**:connect 的 per-会话 executor 线程泄漏是当前主要瓶颈,50 连接以上线程爆炸导致饱和
- **下一步**:修复 executor 泄漏 → 重压验证(预期连接数上限大幅提升、P99 回落)

# IM 下行投递:从"时好时坏"到"一个 group 一个节点"

> 自研 IM(QuantumLink)水平扩展后下行消息丢失实录
> 技术栈:Java 17 · Netty · RocketMQ · Redis · MySQL · Nacos
> 场景:chat 业务层 → RocketMQ(server2client)→ 多 connect 节点 → 推送给目标用户

---

## 一、序言:一个"重启一下就好了"的诡异 bug

水平扩展做完的那天,我信心满满地起了两个 connect 节点,准备验证跨节点互聊:

- 节点 A(19001)连用户甲,节点 B(19002)连用户乙
- 甲发消息给乙 → chat 落库 → 回 ACK → 打 tag 精准投递 → 乙的节点消费 → 推送

第一次跑,乙收到了。第二次跑,乙收不到。第三次,又收到了。**时好时坏,完全没有规律。**

更折磨人的是它的表现像极了环境问题:
- 重启 connect 节点 → 好了
- 过一会儿再测 → 又坏了
- 单节点(只起一个 connect)时 → **从来没坏过**

我花了很长时间怀疑 aTrust(深信服企业安全代理)、Windows 防火墙、系统出站连接占用端口……把环境翻了个底朝天,最后才回到 RocketMQ 本身——**发现是一个消费端语义的经典陷阱:多节点共享了同一个 consumer group。**

这篇文章记录的就是这个坑:从现象、到三层原理(RocketMQ 的 topic/group/tag 到底是什么)、到修复,以及最终沉淀的设计。

---

## 二、先建立正确的 RocketMQ 世界观:Topic / Group / Tag 三个概念

在讲 bug 之前,必须把 RocketMQ 的消息模型讲透——**这个 bug 之所以难查,就是因为"三个概念各自都对,组合起来才是坑"。**

### 2.1 Topic:消息的存储容器,物理上是一组队列

```
Topic "server2client"
  ├── queue 0   ← 每份队列是一串有序消息 + 一份独立的消费进度(offset)
  ├── queue 1
  ├── queue 2
  └── queue 3
```

- Topic 不是"一个桶",是**一组队列**(默认 4 个)
- 消息写进 topic 时落在**某一个队列**:producer 决定(默认轮询、或按 key 哈希、或自定义选择器)
- **队列数 = 该 topic 的并发上限**:一个队列同一时刻只被一个消费者顺序拉取,4 个队列 = 最多 4 个消费者并行消费

### 2.2 Consumer Group:消费端的"身份标签"

消费者启动时必须声明一个 group 名,broker 按名字**分组记账**:

```
group "G1":消费者 A、B、C
  → 队列 0/1/2/3 被分摊给 A/B/C
  → 一条消息只被 A/B/C 中一人消费
  → 全组共用一个消费进度

group "G2":消费者 D(单独)
  → 独自持有全部 4 个队列
  → 每条消息 D 都会消费到
  → 自己有独立的消费进度
```

**核心规则(面试必背):**

> **同一 group 内 = 分摊**:一条消息只被组内一个消费者消费,进度共享。
> **不同 group 间 = 广播**:一条消息每个组都能消费一份,进度独立。

Group 不是"路由地址",而是**记账身份**——它决定"队列持有权"和"消费进度"。

### 2.3 Tag:消息身上的标签,在"拉取响应"时过滤

```
消息结构: [topic][tag][body]
消费者订阅: subscribe("server2client", "tag=127.0.0.1:19002")
```

**tag 过滤的时机**:消费者拉取队列时,broker 先把队列里的消息按订阅表达式过滤,只把匹配的返回。

**tag 不是"路由",是"筛选条件"**——它决定"从你持有的队列里,把哪些消息给你"。

### 2.4 三个概念的关系(用图书馆类比)

| RocketMQ | 图书馆类比 |
|----------|-----------|
| Topic | 图书馆(4 个书架 = 队列) |
| 队列 | 书架(每架的书 = 消息,有序) |
| producer | 出版社(放书,不管谁来看) |
| Consumer Group | **读者证**(同名 = 合伙看,一本只借一人;异名 = 各看各的,每人都有副本) |
| Tag | 书分类标签(武侠/科幻),管理员按读者证给对应分类 |
| 消费进度 offset | 每张读者证各记"看到第几本" |

## 三、Bug 现场:两层机制组合出的"静默丢失"

### 3.1 我的原设计(以为天衣无缝)

```
[chat 下行发送]
1. 查 Redis 会话表 im:session:{userId}:{deviceId} → 得到 nodeId
2. producer.send(msg, tag=nodeId)  → 投进 server2client

[connect 消费]
3. 每个节点 subscribe("server2client", tag=自己的 nodeId)
4. 只消费自己的消息 → 推给本地用户
```

逻辑上完全自洽:tag 精准过滤,每个节点只拿自己的。**单节点时它确实一直是对的。**

### 3.2 加上第二个节点后

两个节点都用硬编码的同一个 group:`new DefaultMQPushConsumer("im-connect-consumer")`。

于是 broker 的视角变成:

```
topic server2client(4 个队列)

group "im-connect-consumer":
  节点 A(订阅 tag=19001) → 被分到 queue 0、1
  节点 B(订阅 tag=19002) → 被分到 queue 2、3
```

### 3.3 消息怎么丢的(完整推演)

```
chat 发一条 tag=19002 的消息
  → producer 默认轮询选队列 → 落在 queue 1

queue 1 的持有者是谁?→ 节点 A(它订阅 tag=19001)

节点 A 拉 queue 1 → broker 按 A 的订阅过滤 → tag=19002 不匹配 → 不发给 A
节点 B 只持有 queue 2/3 → 根本不会去拉 queue 1

结果:消息既被 A 过滤掉,B 又够不到 → 卡死在 queue 1,等于丢了
```

**两个"各自正确"的事实组合成了 bug:**

1. **tag 过滤生效了**(A 确实拿不到 19002 的消息)——正确
2. **队列被分摊了**(B 不持有 queue 1)——也是 RocketMQ 的正常语义
3. 但合在一起:**消息落错了队列,正确的消费者就永远够不到它**

### 3.4 为什么"时好时坏"

chat 下行发送用的是**默认 round-robin 选队列**(没有队列选择器):

- 消息恰好落在 B 持有的 queue(2/3)→ **正常**
- 消息落在 A 持有的 queue(0/1)→ **卡死**

50% 概率,完全随机。加上 RocketMQ 消费者掉线/上线会触发**重平衡(rebalance)**,队列分配还会变——所以表现是"重启一下好了、过一会儿又坏",极度迷惑。

### 3.5 为什么单节点时没问题

一个 group 一个消费者 = 持有全部队列 = 消息落哪个队列都能消费。**这个 bug 只有多节点共享 group 时才暴露**,而它是水平扩展的必经之路——所以它是"水平扩展第一课"级别的经典坑。

## 四、修复:一个 group 一个节点

### 4.1 改动(就一行)

```java
// 修复前:所有节点共享(硬编码)
new DefaultMQPushConsumer("im-connect-consumer")

// 修复后:每个节点独立(group 名带 nodeId)
new DefaultMQPushConsumer(
    "im-connect-consumer-" + nodeId.replaceAll("[:.]", "_"));
// 例:im-connect-consumer-127_0_0_1_19001
```

`replaceAll("[:.]", "_")` 是因为 RocketMQ group 名只允许 `^[%|a-zA-Z0-9_-]+$`,nodeId(`127.0.0.1:19001`)里的冒号和点都要转掉。

### 4.2 为什么这就修好了

```
group-19001(只有 19001 一个消费者)→ 独享全部 4 个队列 + 按 tag=19001 过滤
group-19002(只有 19002 一个消费者)→ 独享全部 4 个队列 + 按 tag=19002 过滤
```

**单消费者 = 持有全部队列 = 消息落哪个队列都必能拉到;再按 tag 过滤 = 只取自己的。**

- group 负责"能拿到所有队列"(正确性)
- tag 负责"只处理自己的消息"(扩展性)

两个机制各管一件事,缺一不可。

### 4.3 修复后的消息流转(最终形态)

```
① chat:查会话表 → nodeId=127.0.0.1:19002 → send(msg, tag=127.0.0.1:19002)
② broker:消息进 server2client 的某个队列(轮询,无所谓哪个)
③ group-19001 拉队列 → broker 按 tag=19001 过滤 → 不是自己的,不返回
④ group-19002 拉队列 → broker 按 tag=19002 过滤 → 匹配,返回给 19002
⑤ 19002 节点 → 查本地 ChannelManager 找用户 → 推送
```

## 五、修复后审视:这套设计的优点与代价

### 5.1 优点

- **正确性**:消息永不因"落错队列"而丢
- **扩展性**:加节点 = 加一个 group,零配置(nodeId 自动派生,三处一致天然成立)
- **职责分离**:上行保序(队列选择器 + Orderly 消费)和下行投递(独立 group + tag)互不干扰

### 5.2 代价(面试深挖点)

**① 拉取放大**:广播语义下,每个 group 都拉全量队列。N 个节点 = broker 要给 N 份拉取响应,每个节点消费全量再过滤。节点少时无所谓,几十个以上是硬伤。

**② 消费并发上限 = 队列数**:单 group 单消费者的并发上限就是 topic 的队列数(默认 4),下行量大了要调大队列数。

**③ 节点宕机 → 消息积压,不会被接管**:group 位点独立,节点 A 挂了它的消息积压,恢复后继续消费。对 IM 这是**正确的**(宕机期间用户连接也断了,上线走离线拉取,积压推送补上不重复)。

### 5.3 演进路径(大厂怎么做)

节点规模上去后,业界会从"独立 group + tag 过滤"演进到**队列级路由**:

```
producer 按目标 nodeId 选队列(MessageQueueSelector)
→ 每个节点只消费自己那部分队列
→ 可以共享 group、并发更高、broker 拉取压力不放大
代价:节点增删时队列重分配、位点迁移,复杂度高
```

**当前阶段"独立 group + tag"是简单正确的第一版本,队列路由是扩展极限的第二版本**——面试讲出这条演进路径就完整了。

## 六、排查过程复盘:我走过的弯路(同样值钱)

这个 bug 花了很久,复盘出的教训对面试很有用:

### 弯路 1:怀疑环境(最大的时间黑洞)

"时好时坏 + 重启变好"极其像环境问题。我怀疑过:
- 深信服 aTrust(企业安全代理,会按进程注入 RST)——**不是它**
- Windows 防火墙 / Defender——**不是它**
- connect 端口落在动态端口范围内被系统连接占用——**不是它**

**教训:先怀疑自己代码里的"多组件组合语义",再怀疑环境。**"重启变好"不是环境证据,而是"某种随机分配"(rebalance / round-robin)的证据——随机分配是**代码语义问题**的标志。

### 弯路 2:用垃圾探针制造假证据

我写探针测试时,`Buffer.alloc(64)` 发了**全零字节**,服务端报 `bad magic: 0` 并 RST——我把这个当成了"环境在掐连接"的证据,误导了好几个来回。

**教训:探针必须先跑通"已知正常"的路径,再改变量。** 用垃圾数据测,测出的全是垃圾结论。

### 弯路 3:忽略"单节点正常"这个最强线索

单节点从不出错,是最重要的线索——它直接指向"多节点共享的东西"。consumer group 是唯一被共享的消费语义。

**教训:复现条件越窄,根因越近。**"只有多节点才坏"≈"多节点共享的状态坏了"。

## 七、面试问答(11 连)

**Q1:为什么多节点共享 consumer group 会丢消息?**
同一 group 内队列被分摊,消息落错队列后目标节点够不到。tag 过滤在"拉取时"生效,但"谁有资格拉这个队列"由 group 决定——两个机制组合才完整,共享 group 破坏了后者。

**Q2:topic 和 group 是什么关系?**
正交。一个 topic 可以被多个 group 独立并行消费(广播),每个 group 各记各的位点;同一 group 内才分摊。

**Q3:producer 发消息时知道 group 吗?**
不知道。producer 只认 topic(和 tag),消息进队列躺着;group 是消费端身份,消费时 broker 才知道。

**Q4:tag 过滤发生在什么时候?**
消费者拉取队列时,broker 按该消费者的订阅表达式过滤,只返回匹配的消息。**tag 不路由,只筛选。**

**Q5:为什么单节点时不丢、加节点就丢?**
单 group 单消费者持有全部队列,消息落哪个队列都能消费;共享 group 后队列被分摊,"落错队列"才成为可能。

**Q6:为什么重启会"变好"?**
重启触发 rebalance 重分配队列,加上 producer 轮询选队列的随机性——短暂地"碰巧正常",不是修复。

**Q7:修复方案为什么是"独立 group"?**
独立 group = 单消费者独享全部队列,消息落哪个队列都能拉到;再按 tag 过滤只取自己的。正确性(group)和扩展性(tag)各管一件事。

**Q8:独立 group 的代价是什么?**
广播语义:每个 group 都拉全量队列,节点多时 broker 拉取压力 N 倍放大;单节点消费并发上限 = 队列数。

**Q9:大厂怎么解决拉取放大?**
队列级路由:producer 按 nodeId 选队列,节点只消费自己那部分队列,共享 group 也不冲突。代价是节点增删时的队列重分配和位点迁移。

**Q10:节点宕机时消息会怎样?**
独立 group 位点积压,恢复后继续消费,不丢。IM 场景下这是正确的——宕机期间用户连接也断了,上线走离线拉取,积压推送补上不重复。

**Q11:为什么说这是"水平扩展第一课"?**
单节点时共享 group 天然正确,只有水平扩展才暴露;而且表现是"概率性丢消息、时好时坏",极难排查——任何做长连接多节点的人都会撞一次。

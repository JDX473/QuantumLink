# 慢客户端处理方案(IM 下行推送背压与补偿设计)

> 目标:在"一个客户端网络差/接收慢"的情况下,**不拖垮整个接入层节点**,同时**不丢消息**,并且**不误伤健康客户端**。
> 本文档为本系统(QuantumLink)贴合版——去掉通用方案里的"离线消息表"(本系统没有),改为复用已有的"落库 + seq 位点增量拉取";并补上"不可达 → 主动断连"以触发补偿。

---

## 0. 问题定义

**慢客户端(slow consumer)**:一个客户端与 Netty 接入层之间的网络变差,导致:

- 服务端向它推送时,内核发送缓冲 / Netty outboundBuffer 写不进去
- 无脑写 → 积压传染:outboundBuffer → EventLoop 任务队列 → 节点内存 → OOM
- 无脑丢 → 消息永久空洞,违背 IM"消息不丢"承诺

**关键认知**:
1. **Netty writeAndFlush 不阻塞、不卡线程**——写不出去只积压在 `ChannelOutboundBuffer`,"天然背压"是错觉
2. **MQ 消费者与 channel 写之间没有背压**——慢客户端本质是"上游(MQ 消费)速率 > 下游(单 channel 写)速率,无负反馈"
3. **正确方向不是给慢客户端发明新逻辑,而是降维成"暂时离线用户",复用已有可靠性(落库 + 重连拉取 + 增量同步)**

## 1. 四层设计总览

| 层级 | 手段 | 解决什么 | 本系统现状 |
|---|---|---|---|
| L1 | Netty WaterMark + 停读 | 背压信号存在,防单 channel 写爆内存 | ⚠️ 只加了 isWritable 跳过,水位/停读未配 |
| L2 | 有界发送队列 + 明确队满行为 | 慢客户端消息"不丢、不无限积压" | ❌ 未做 |
| L3 | 补偿通道(客户端主动补拉) | 被丢的消息能回来,不靠手动重进 | ✅ 已有(增量拉取) |
| L4 | 降维:慢客户端 = 暂时离线 | 复用离线可靠性 | ✅ 架构支持(落库+拉取) |

> 原则:**L1 是地基,L4 是终点**;落地优先级 L1 → L4,中间层按需取舍。

## 2. L1:Netty 写水位 + 停读(背压信号,必做)

### 2.1 问题

`channel.isWritable()` 默认依赖 `WRITE_BUFFER_WATER_MARK`,但 Netty 写缓冲默认可无限增长——超过 high 只是 `isWritable=false`,数据照样写。**本系统当前只做了"isWritable() 跳过推送"(DownstreamConsumer),但没配水位、没停读**——"跳过推送"减负了,但没形成"背压回传"。

### 2.2 设计

```java
// 每个连接设置水位(low/high 根据单消息平均大小 + 连接数调优)
ch.config().setWriteBufferWaterMark(new WriteBufferWaterMark(8 * 1024, 32 * 1024));
```

```java
// 写不动 → 停读(TCP 接收窗口不再消费,背压回传客户端)
if (!ch.isWritable()) {
    ch.config().setAutoRead(false);
    // 记录该 channel 进入"受限"状态
}
if (ch.isWritable()) {
    ch.config().setAutoRead(true);
}
```

**为什么停读**:一条 TCP 连接读写同一根管子,写不出去通常意味着对方收不动——停读让背压往回传导到客户端,让它自己感受"我发太快了",而不是服务端把压力全揽进内存。

**超时兜底**:channel 长时间"受限"(如 N 秒)→ 判定不可达 → 走 L4(主动断连,见 L4)。

## 3. L2:有界发送队列 + 明确队满行为(可选但推荐)

### 3.1 设计

per-channel(或 per-EventLoop)**有界**发送队列,不能全局共享(否则一个慢客户端占满全局队列拖累所有人)。

**队满行为(三选一,必须有明确语义)**:
- **等(推荐)**:队满即背压,停读降速,不丢——适合实时性要求高的场景
- **丢(需配合 L3)**:队满则丢,但必须**消息已落库 + 有可复用拉取路径**,丢才不算丢
- **拒(最差)**:生产者抛异常,把压力抛回上游,通常不选

### 3.2 关键点

- 队满后的判定(攻击 vs 正常慢)不能只看队列深度,要结合连接存活时间、是否完成鉴权——**避免误伤正常弱网用户**
- **删 token 是错的**:攻击者不靠 token 重连(一直新建连接);删 token 只惩罚被误判的正常弱网用户(被迫重新登录)。正确做法:**关连接即可,token 保留,靠重连拉取补偿**

### 3.3 MQ 位点:提交

**队满丢消息,MQ 位点必须提交**。消息已落库,丢的是"实时推送"这一跳,用户可经重连/增量拉取拿回。不提交 → RocketMQ 无限重投 → 拖死整个 tag 队列(队列级头阻塞),影响所有健康用户——比丢一条消息严重得多。

## 4. L3:补偿通道(本系统已有,无需新建)

### 4.1 为什么必须补偿

"靠用户重新进会话"是错的——弱网用户挂在会话里,不会主动退出重进,消息就是永久空洞。

### 4.2 本系统的补偿(已具备)

- **落库**:消息先落 `im_message` / `im_group_message`(可靠性锚点)
- **位点**:客户端维护每会话最大已收 seq(`conversationLastSeq` / 会话内缓存游标)
- **增量拉取**:客户端在重连后 / 打开会话时,`GET .../messages?afterSeq=` 从 seq 位点补齐空洞

**这就是 L3,不用新建**——本系统"落库 + seq 位点拉取"天然是补偿通道。

### 4.3 一个必须补的缺口:触发时机

**弱网客户端"还连着、心跳没断",服务端把它当离线丢推送了,但客户端不会自动重连 → 补拉不触发。** 要堵,二选一:
- **方案 A(推荐)**:判定不可达后,服务端**主动 close 连接** → 客户端必然触发重连 → 重连后增量拉取补齐。把"当离线"落实成"真正断开",重连就是天然补偿触发。
- 方案 B:客户端在会话内也定期增量拉取(心跳之外的同步定时器),网络恢复后自动补齐。

**A 更符合"降维"精神**——真断开,复用重连路径,比客户端多跑一个定时器简单。

## 5. L4:降维——慢客户端 = 暂时离线(最终方向)

### 5.1 核心思想

**不要再为慢客户端发明新逻辑。** 服务端在推送不可达时,只做一件事:**把该用户降级为"暂时离线"**,走已有的离线可靠性路径。

### 5.2 落地(本系统)

```
判定不可达(isWritable=false + 超时 / 停读超时 / channel 断开)
  → 不推(消息已落库)
  → 【主动 close 连接】(补上的关键:让客户端触发重连)
  → 客户端重连 → 握手 → 增量拉取 → 消息补齐
  → 服务端不需要"慢客户端专用队列",只需要"判定不可达 → 复用离线链路"
```

### 5.3 为什么这是终点

本系统可靠性体系(落库、seq 位点、增量同步、重连拉取)**就是为"不可达"设计的**。慢客户端只是"暂时不可达"。复用,比新造简单且正确。

### 5.4 实时性牺牲

有界、可控——只在"不可达"期间实时性降级,网络恢复后自动补齐。比起"拖垮节点"或"永久丢消息",这是正确取舍。

## 6. 坑(面试官会照这个问,答案已定)

| 坑 | 错误答案 | 正确答案 |
|---|---|---|
| "writeAndFlush 会阻塞消费线程" | 卡住消费者=天然背压 | 不阻塞,写不出去只进 outboundBuffer |
| 积压位置 | 只盯 outboundBuffer | 积压会换地方(任务队列、握手缓冲)——换地方积压 ≠ 解决 |
| 队满处置 | 删 token | 关连接即可,别惩罚正常弱网用户 |
| MQ 位点 | 不提交 | 提交,避免无限重投拖死队列 |
| 补偿触发 | 靠用户重新进会话 / 靠客户端定时器 | **服务端主动断连 → 重连自动触发增量拉取**(本系统补上的一环) |
| 慢客户端本质 | 发明新机制 | 降维成"暂时离线",复用离线可靠性 |

## 7. 一段能直接讲给面试官的口述

> "我处理慢客户端,核心是四个字:**有界 + 降维**。
> 有界:Netty 配 WaterMark + 停读,让背压回传到客户端;再配 per-channel 有界发送队列,队满不无脑丢、不无脑等,而是明确判定不可达(MQ 位点照常提交,避免无限重投拖死队列;关连接即可,不删 token 不惩罚正常弱网用户)。
> 降维:不可达就**主动断开连接**,让客户端触发重连,复用已有的落库 + seq 位点增量拉取把消息补齐——不依赖用户手动操作,也不给慢客户端设计新逻辑。
> 一句话:**我不给慢客户端设计新逻辑,我让它复用'离线'的可靠性路径,把'实时'降成'稍后到达',并且保证它一定能到达。**"

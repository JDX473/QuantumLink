## 一、v1 的教训:假瓶颈污染

v1 报告的数据被多个**假瓶颈**污染,结论不可信。复盘:

| 假瓶颈 | 真相 | 影响 |
|--------|------|------|
| console.log 阻塞客户端 | client-core 每条消息打日志,30 连接 700 条/秒同步写 stdout,Node 事件循环被卡 | v1 的 3.6s 延迟主因 |
| MySQL CLI 100ms | mysql 命令行每次新建连接 100ms(认证开销),chat 用连接池毫秒级 | 误判 MySQL 慢 |
| mqadmin 逐条 2.4s | 每条启动一个 JVM | 误判 broker 慢 |
| 压测数据累积 | 每次新建用户/会话不清理,Redis 8 万 key / MySQL 消息堆积 | keys 扫描变慢、表变大 |
| 压测脚本发送速率 bug | sendInterval 公式错,目标 90 实际 905 条/秒超载 | 超载压垮系统 |

**v2 修正:静默模式 + 每轮独立用户 + 清理脚本 + 多进程客户端 + 修正发送速率。**

## 二、v2 压测数据(干净环境 + 多进程客户端)

| 配置 | 发送 | 真实负载(MSG+DELIVER_ACK) | P50 | P99 |
|------|------|---------------------------|-----|-----|
| 15 连接(1 进程) | 81 条/秒 | 164 条/秒 | **34ms** | 79ms |
| 30 连接(2 进程) | 164 条/秒 | 328 条/秒 | **61-76ms** | 178-220ms |
| 60 连接(4 进程) | 328 条/秒 | 656 条/秒 | **~310ms** | ~680ms |

**关键结论**:
1. **30 连接 328 真实负载时系统健康(P50 61-76ms)**——链路可靠
2. **60 连接 656 真实负载时 chat CPU 57%(接近饱和),P50 300ms**——系统瓶颈出现
3. 消息 100% 落库(0 丢失),幂等可靠

**单 Node 进程 30 连接(P50 641ms)vs 双进程各 15 连接(P50 61ms)**:同样的连接数和负载,分散客户端后延迟降 10 倍——**v1 的"100 连接崩溃"很大程度是客户端瓶颈,不是系统**。

## 三、真实瓶颈定位(修复后)

### 已修复(压测驱动)

| 瓶颈 | 修复 | 验证 |
|------|------|------|
| per-会话 executor 线程泄漏(200 连接 439 线程) | 共享有界线程池 48 槽 + hash 路由 | 线程固定 48,不再增长 |
| Redis keys 扫描(O(N) 阻塞) | 设备 Set `im:devices:{uid}` + SMEMBERS | 移除全部 keys 扫描 |
| 客户端 console.log 阻塞 | client-core 加 quiet 模式 | 30 连接延迟 6 倍改善 |

### 当前瓶颈(60 连接出现)

**chat 业务处理 CPU(57% 饱和)**。chat 每条消息:Orderly 消费(JSON 解析)→ 幂等 SETNX → Redis INCR → 落库 → **fillSenderProfile 查 DB** → 下行推送。656 负载时 chat 单实例 CPU 接近饱和。

**优化方向**:
1. ~~**fillSenderProfile 缓存**~~ **✅ 已实现(2026-08-05)**:`UserCacheService`(Redis `im:user:{uid}` 只缓存 username/avatarUrl,TTL 10min,改头像 invalidate)
2. **增大 MQ 队列数**:Orderly 消费并发 = 队列数(16),可加大提升消费并发(未做)
3. ~~**chat 多实例**~~ **✅ 已验证(2026-08-05)**:双实例消费分摊(共享 group),实例稳定后同会话 seq 严格有序、雪花 id 唯一

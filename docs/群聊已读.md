# 群聊已读:成员水位 + 预聚合计数(按需查询)

> 一句话结论:**群聊已读 = 成员水位(和单聊同构)+ 每消息预聚合计数,查询 O(1),不广播。** 核心差异:单聊只有一个对端,靠推 READ 事件;群聊 N 个成员,推广播 = 写放大,改成"上报时预聚合、需要时查"。协议零改动(复用 READ_ACK + read_report)。

---

## 一、产品语义(先定清楚)

| 问题 | 决策 |
|---|---|
| 显示什么 | 每条群消息底部"**n人已读**"(发送者知道自己发的消息几人看到) |
| 实时性 | **不实时推**,按需查(打开群拉取时批量带已读数) |
| 显示口径 | `count - 1`(排除发送者自己,微信也这样) |
| "谁读了" | 先不做列表;需要时按成员水位筛(不常查) |

## 二、为什么群已读比单聊难:读扩散缺一个维度

单聊能靠水位,因为**会话天然是两个人的**:B 的水位覆盖 B 对 A 所有消息的已读。

群聊是**读扩散**——`im_group_message` 里**一份消息**,没有"每个成员一份"可以挂"他读没读"。要回答"这条有几人读过",必须**新增一条"群成员 × 群消息"的已读记录维度**。这是全部难点的根源,也是和单聊已读分道扬镳的原因。

## 三、数据模型:成员水位 + 预聚合计数

```
① 成员水位(和单聊已读同构)
   im:group_read:{groupId}:{memberId} → maxReadSeq
   "B 读到群内第 50 条" = ≤50 全读过

② 每消息已读计数(预聚合,群聊新增)
   im:group_msg_read:{groupId}:{seq} → count
   "第 30 条被 n 个成员读过"
```

**为什么两个结构**:水位回答"某成员读到哪"(成员视角),计数回答"某条几人读"(消息视角)。单聊只有水位——因为对端就一个,发送方用对端水位本地推导即可;群聊面向 N 个成员,必须把"消息视角"的聚合结果单独预存,否则查询时扫所有成员水位是 O(群成员数)。

## 四、核心机制:预聚合(讲对的关键)

**计数不是"查询时扫成员水位聚合",是"上报时增量维护"。**

- **查询时聚合**:查"第 30 条几人读" = 扫所有成员水位、数几个 ≥ 30 → O(N),200 人群查一次读 200 个 key。按需查场景下反而贵。
- **上报时预聚合(本方案)**:B 打开群读到 20~50 条,上报一次 `untilSeq=50` → 服务端水位 20→50 推进时,对 (20,50] 每条消息 INCR 一次 → 查询变纯 `GET`,O(1)。

```
B 打开群 → 上报 {groupId, untilSeq=50}
服务端:B 水位 20 → 50
  → 对 (20, 50] 区间每条消息 INCR 一次计数
  → 第 21~50 条各 +1

查询"第 30 条几人读" = GET im:group_msg_read:{gid}:30 → O(1)
```

**为什么"批量读"是预聚合的完美抓手**:B 打开群一次读到几十条,上报一次 → 服务端只做几十次 INCR(Lua 一次原子完成)。写放大 = "读的批量大小",不是"人 × 消息"。

## 五、完整链路(落到现有代码)

```
① B 打开群(客户端)
   复用 READ_ACK 帧 + read_report topic——协议零改动
   B 上报 {conversationId=groupId, untilSeq=可见最大seq}
   (conversationId 就是群 id,`g_` 开头,connect 照旧转发)

② chat ReadAckConsumer 消费 read_report → ReadService

③ ReadService 分支:
   conversationId 以 g_ 开头 → 群已读路径:
     - 鉴权:readerId 是群成员(GroupService.isMember,替代单聊的 isConversationParticipant)
     - 成员水位原子推进 + 区间 INCR(见第六节 Lua)
   conversationId 以 # 开头(A#B)→ 单聊路径(现有,不碰)

④ 查询(按需):
   GET /api/groups/{gid}/messages?afterSeq=... 响应里每条带 readCount
   —— 打开群一次拿全部消息的已读数,渲染直接显示"n人已读"
```

**服务端唯一鉴权改动点**:`ReadService.handleReadReport` 现在校验 `isConversationParticipant`(A#B 拆分),群聊要换成 `isMember`。

## 六、并发与原子(正确性关键)

水位推进 + 区间 INCR 必须**原子**,否则两个设备/两个 chat 实例并发上报会重复计数或漏加。用一段 Lua(和单聊水位、面对面建群同一套路):

```lua
-- KEYS[1] = im:group_read:{gid}:{member}
-- ARGV[1] = untilSeq, ARGV[2] = 计数前缀 im:group_msg_read:{gid}:
-- ARGV[3] = TTL
local cur = tonumber(redis.call('GET', KEYS[1]) or '0')
if cur >= tonumber(ARGV[1]) then return 0 end      -- 水位没推进(乱序/重复),忽略
redis.call('SET', KEYS[1], ARGV[1], 'EX', ARGV[3])
for s = cur + 1, tonumber(ARGV[1]) do               -- 区间内每条消息计数 +1
  redis.call('INCR', ARGV[2] .. s)
  redis.call('EXPIRE', ARGV[2] .. s, ARGV[3])
end
return 1
```

Redis 单线程执行 Lua,整体原子,保证:
- **水位只进不退**(cur ≥ untilSeq 直接忽略)→ 多端、乱序、重复上报安全
- **推进与计数同块** → 不存在"水位动了计数没加"的中间态(chat 崩溃在 Lua 前 = 全没发生;后 = 全发生)
- **多 chat 实例共享 Redis 计数器** → Lua 单线程天然串行,实例并发不重号

## 七、存储决策:为什么只用 Redis(和单聊不同)

| | 单聊已读 | 群已读 |
|---|---|---|
| 落 MySQL? | ✅(`im_read_pos`) | ❌ 不落 |
| 为什么 | 影响历史展示(重进会话看对端读没读),持久事实 | "n人已读"是瞬时展示,老消息的已读数没人关心 |
| 丢失后果 | 需要可追溯 | Redis 丢 = 显示 0,成员重开群重新上报即重建,**自愈** |

- 计数 key **TTL 7 天**(老消息不需要已读数)
- 水位 key **TTL 30 天**(成员活跃期内不会过期)

**"可重建的瞬时数据放 Redis"是典型用例**——和单聊已读(持久事实落 MySQL)正好形成对比,面试可直接讲这个存储决策差异。

## 八、异常面分析(诚实,按类处理)

### A 类:正确性关键 → Lua 原子强制(不是 happy path)

| 异常 | 兜底 |
|---|---|
| 两个设备并发上报 | Lua 水位只进不退,后到忽略 |
| 乱序上报(先 50 后 30) | 同上,幂等 |
| 水位推进 + 计数 INCR 的原子性 | 合成一段 Lua,无中间态 |
| 多 chat 实例并发 | Lua 单线程串行 |

### B 类:展示偏差 → 接受自愈,不为展示增强上复杂度

| 异常 | 处理 |
|---|---|
| READ_ACK 上报丢失(网络断) | fire-and-forget,丢了该成员这次没计入;下次打开群重新上报,**最终一致** |
| Redis 重启,水位+计数全丢 | 成员重开群重新上报 → 自动重建;老消息已读数本来就该过期 |
| 水位 TTL 过期后重复计数 | 水位 TTL(30天) > 计数 TTL(7天),窗口极窄;接受轻微偏差 |
| 成员退群后计数残留 | 计数含历史成员,轻微偏差;或按当前成员过滤(查询时,不常查) |

### C 类:客户端约束(设计要写死)

| 约束 | 说明 |
|---|---|
| **客户端必须只上报实际渲染的最大 seq** | 打开群渲染了最近 100 条 → 上报可见最大 seq;报 serverMaxSeq 会把没显示的老消息虚高算已读 |

### D 类:明确不做

- 已读上报的重传/ACK(展示增强,丢了自愈)
- 群已读落 MySQL(瞬时数据)
- 群已读实时推送(广播 = 写放大,方案选择)
- 精确"谁读了"列表(需要时按成员水位筛)

**面试讲法**:我把异常分三类——① 并发/乱序/多实例/原子性这类正确性关键用 Lua 钉死;② Redis 重启/上报丢失/水位过期这类展示偏差接受自愈或轻微偏差(已读是展示增强不是可靠性锚点);③ 客户端必须只上报实际渲染的 seq(设计约束)。不为展示增强上消息级的可靠性机制。

## 九、边界情况

| 场景 | 处理 |
|---|---|
| 发送者自己算不算 | 计数含所有成员(发送者打开群也算),显示时 count-1 |
| 离线成员 | 不上报不计入;上线打开群上报后补上 |
| 新成员入群 | 水位从 0 开始,上报可见范围(尾部),只计入实际看过的 |
| 多设备 | 水位用户级(同单聊),手机读的电脑也算 |
| 计数 key 无限增长 | TTL 7 天自动消失 |
| 大群 | 本方案面向小群(≤200,面对面建群上限);大群仍待写扩散方向 |

## 十、改动清单

| 层 | 改动 |
|---|---|
| 协议 | **零改动**(复用 READ_ACK 帧 + read_report topic) |
| 服务端 | `ReadService` 加 `handleGroupReadReport`(g_ 分支:Lua 水位推进 + 区间 INCR);`GroupService.pullGroupMessages` 响应每条带 `readCount` |
| 存储 | Redis:`im:group_read:{gid}:{member}`(30天)、`im:group_msg_read:{gid}:{seq}`(7天) |
| 客户端 | `reportRead` 放开群聊(`currentConvIsGroup` 不再挡住);群消息渲染时显示"n人已读" |

# 群聊已读:完整设计方案与实现(成员水位 + 预聚合计数 + 只推发送者)

> 一句话结论:**群聊已读 = 成员水位(和单聊同构)+ 每消息预聚合计数,查询 O(1);不群广播(写放大),实时只推给受影响消息的发送者。** 协议零改动(复用 READ_ACK + read_report),存储仅 Redis + TTL(可自愈)。本文从产品语义到异常面逐层展开,含实现细节与两个实测修复。

---

## 0. 结论(先给答案)

| 维度 | 决策 |
|---|---|
| 数据模型 | 成员水位 + 每消息预聚合计数 |
| 上报 | 复用 READ_ACK 帧 + read_report topic(协议零改动) |
| 实时性 | 不群广播;推进时**只推给受影响消息的发送者**(区间 ≤ 20 条) |
| 查询 | 拉取接口每条消息带 readCount,O(1) |
| 存储 | 仅 Redis(水位 30 天 / 计数 7 天),丢失自愈 |
| 正确性 | 并发/乱序/多实例靠 Lua 原子;发送者自动计入 |

## 1. 产品语义

| 问题 | 决策 |
|---|---|
| 显示什么 | 每条群消息底部"**n人已读**"(发送者知道自己发的消息几人看到) |
| 发送者自己算不算 | 算(发送者已看到自己的消息),界面 count-1 显示"其他已读人数" |
| 实时性 | 发送者在会话内时**实时**看到计数增长(只推给自己);其他成员重开可见 |
| "谁读了"列表 | 先不做;需要时按成员水位筛(不常查) |

### 一个核心语义:"已读 = 打开会话的近似",不是"逐条阅读"

水位方案(单聊/群聊同)的**固有特性**:**成员打开会话拉到最近 N 条、上报最大 seq → 更早没拉到的消息也会被判已读**。

```
B 离线,A 发了 150 条;B 重新登录只增量同步了最近 100 条(seq 51~150)
  → B 上报"已读到 seq 150"
  → seq 1~50(那 50 条 B 根本没拉到、没看到)也被标已读
群聊同理:成员打开群只加载最近 100 条,上报 maxSeq,更早的群消息也全标已读
```

**这不是 bug,是设计选择**:
- 已读在产品语义上是"**会话被打开过**",不是"每条都逐字看了"(微信/主流 IM 一致:打开会话未读清零,哪怕历史没逐条看)
- 水位用"**一个数字**"表达"≤seq 全读",换来状态 O(1) + 查询 O(1)
- **代价**:无法表达"精确到条的部分阅读"(读到最近 10 条但前面仍标未读)——IM 会话场景不需要这种精确,所以水位是主流;需要精确的场景(如阅读类 IM、进度)才用逐条标记

## 2. 为什么群已读比单聊难:读扩散缺一个维度

单聊能靠水位,因为**会话天然是两个人**:B 的水位覆盖 B 对 A 所有消息的已读。

群聊是**读扩散**——`im_group_message` 里**一份消息**,没有"每个成员一份"可以挂"他读没读"。要回答"这条有几人读过",必须**新增一条"群成员 × 群消息"的已读记录维度**。这是全部难点的根源,也是和单聊已读分道扬镳的原因。

| | 单聊已读 | 群聊已读 |
|---|---|---|
| 让对方知道 | 推 READ 事件给**对端一人**(便宜) | 不能广播(每个成员读一下推全群 = 写放大) |
| 数据模型 | 对端水位 | 成员水位 + **预聚合计数** |
| 查询 | 发送方用对端水位本地推导 | 按需查(拉取接口批量带) |
| 存储 | MySQL 持久 | Redis + TTL(可重建) |

## 3. 数据模型

```
① 成员水位(和单聊已读同构)
   im:group_read:{groupId}:{memberId} → maxReadSeq
   "B 读到群内第 50 条" = ≤50 全读过
   —— 用户级(多端共享:手机读了电脑也算),TTL 30 天

② 每消息已读计数(预聚合,群聊新增)
   im:group_msg_read:{groupId}:{seq} → count
   "第 30 条被 n 个成员读过"
   —— TTL 7 天
```

**为什么两个结构**:水位回答"某成员读到哪"(成员视角),计数回答"某条几人读"(消息视角)。单聊只有水位——对端就一个,发送方用对端水位本地推导;群聊 N 个成员,必须把"消息视角"的聚合结果单独预存。

## 4. 核心机制:预聚合(查询 O(1) 的关键)

**计数不是"查询时扫成员水位聚合",是"上报时增量维护"。**

- **查询时聚合(坏方案)**:查"第 30 条几人读" = 扫所有成员水位、数几个 ≥ 30 → O(群成员数),200 人群查一次读 200 个 key。
- **上报时预聚合(本方案)**:B 打开群读到 20~50 条,上报一次 `untilSeq=50` → 服务端水位 20→50 推进时,对 (20,50] 每条消息 INCR 一次 → 查询变纯 `GET`,O(1)。

```
B 打开群 → 上报 {groupId, untilSeq=50}
服务端:B 水位 20 → 50
  → 对 (20, 50] 区间每条消息 INCR 一次计数
  → 第 21~50 条各 +1

查询"第 30 条几人读" = GET im:group_msg_read:{gid}:30 → O(1)
```

**为什么"批量读"是预聚合的完美抓手**:打开群一次读到几十条,上报一次 → 服务端只做几十次 INCR(Lua 一次原子完成)。写放大 = "读的批量大小",不是"人 × 消息"。

## 5. 上报链路(协议零改动)

```
① 客户端打开群 / 会话中收到新消息
   复用 READ_ACK 帧:上报 {conversationId=groupId, untilSeq=可见最大seq}
   (conversationId 就是群 id,`g_` 开头,connect 照旧转发)

② chat ReadAckConsumer 消费 read_report → ReadService.handleReadReport
   —— 按 conversationId 前缀分流:
      `g_` 开头 → 群已读路径(本节)
      否则    → 单聊路径(对端水位 + 推 READ,不碰)

③ 群路径:
   a. 校验 readerId 是群成员(GroupService.isMember 的等价查询,越权防护)
   b. Lua:水位只进不退 + 区间 INCR(原子)
   c. 实时通知受影响消息的发送者(见第 7 节)

④ 查询(按需):
   GET /api/groups/{gid}/messages?afterSeq=... 响应每条带 readCount
   —— GroupService.pullGroupMessages 用 multiGet 批量取整页计数
```

## 6. 并发与原子:Lua 详解

水位推进 + 区间 INCR 必须**原子**,否则两个设备/两个 chat 实例并发上报会重复计数或漏加。整段 Lua:

```lua
-- KEYS[1] = im:group_read:{gid}:{member}
-- ARGV[1] = untilSeq, ARGV[2] = 计数前缀 im:group_msg_read:{gid}:
-- ARGV[3] = 计数 TTL
local cur = tonumber(redis.call('GET', KEYS[1]) or '0')
if cur >= tonumber(ARGV[1]) then return -1 end    -- 水位没推进(乱序/重复),返回 -1
redis.call('SET', KEYS[1], ARGV[1], 'EX', ARGV[3])
for s = cur + 1, tonumber(ARGV[1]) do              -- 区间内每条消息计数 +1
  redis.call('INCR', ARGV[2] .. s)
  redis.call('EXPIRE', ARGV[2] .. s, ARGV[3])
end
return cur                                          -- 推进时返回旧水位(供实时推送算区间)
```

**返回值设计**:返回**旧水位 cur**(而非 1/0),调用方拿到旧水位才能算出"本次推进的区间 (cur, untilSeq]"→ 用于实时推送哪些消息被新读了。未推进返回 -1。

Redis 单线程执行 Lua,整体原子,保证:
- **水位只进不退**(cur ≥ untilSeq 直接忽略)→ 多端、乱序、重复上报安全
- **推进与计数同块** → 不存在"水位动了计数没加"的中间态(chat 崩溃在 Lua 前 = 全没发生;后 = 全发生)
- **多 chat 实例共享 Redis 计数器** → Lua 单线程天然串行,实例并发不重号

**区间循环的安全性**:范围 = 本次新读条数(打开群读一批 = 几十条,单消息实时读 = 1 条),在 Redis 单线程内是微秒级。极端情况(水位 TTL 过期后从 0 重推)区间可能大,但被"水位 TTL 30 天 > 计数 TTL 7 天"限制在窄窗口,且即时如此也只是几十~几百次 INCR,可接受。

## 7. 实时更新:只推给发送者(非群广播)

### 为什么不能群广播

每个成员读一下就广播全群 = 写放大(和"预聚合"要解决的正是同一件事)。所以群已读**默认按需查**;但"发送者在会话内看到自己消息的已读数"是核心体验,必须实时。

### 折中:只推给受影响消息的发送者

```
B 读了 A 的消息 → 水位推进 → 区间 (old, untilSeq] 内的消息被新读
  → 查这些消息的发送者(一条 SQL:WHERE group_id=? AND seq > ? AND seq <= ?)
  → 把 {groupId, seq, readCount} 只推给这些发送者(≠ 读者自己)
  → 一个事件只影响一个人(该消息的发送者),不是全群
```

- **事件量级**:B 读一批消息,受影响发送者 = 这批消息的不同发送者数(通常 1~3 人),每人几条事件。比群广播小一个量级。
- **区间上限** `MAX_LIVE_PUSH_RANGE = 20`:区间 > 20(批量开群读)跳过实时推送——发送者重开会话时从拉取接口拿到最新计数。避免"B 打开一个 500 条消息的群 → 200 条事件"的突发。
- **协议**:新增 `DownstreamEnvelope.TYPE_GROUP_READ`,connect 映射为 MSG_ACK 帧推给发送方;客户端 `_onAck` 用 `{conversationId, seq, readCount}`(无 readerId/untilSeq)与单聊 READ 区分 → `onGroupRead` 回调 → 渲染层更新该消息的"n人已读"。

### 实时推送 vs 拉取兜底(两条路互补)

| 路径 | 管什么 | 触发 |
|---|---|---|
| 实时 `TYPE_GROUP_READ` | 发送者在会话内,别人读了 → 秒级更新 | 服务端推 |
| 拉取接口 `readCount` | 重开会话 / 批量读场景 / 其他成员 | 客户端拉 |

## 8. 存储决策:为什么只用 Redis

| | 单聊已读 | 群已读 |
|---|---|---|
| 落 MySQL? | ✅(`im_read_pos`) | ❌ 不落 |
| 为什么 | 影响历史展示(重进会话看对端读没读),持久事实 | "n人已读"是瞬时展示,老消息的已读数没人关心 |
| 丢失后果 | 需要可追溯 | Redis 丢 = 显示 0,成员重开群重新上报即重建,**自愈** |

- 计数 key **TTL 7 天**、水位 key **TTL 30 天**(水位 > 计数,防"水位过期后对已读老消息重复计数"窗口扩大)
- **"可重建的瞬时数据放 Redis"是典型用例**——和单聊已读(持久事实落 MySQL)形成对比,面试可直接讲这个存储决策差异。

### TTL 过期后的行为(面试必问:计数 key 会不会无限攒?过期了怎么办?)

- **不会无限攒**:计数 key 只在"有人读它"时才创建(没人读的旧消息不建 key),且 7 天自动过期 → 同一时刻活跃的 key ≈ "最近 7 天被读过的新消息",是**滑动窗口**而非全历史。粗算:每天 1 万条新消息,峰值 ≈ 7 万个 key × 几十字节 ≈ 几 MB。
- **TTL 到期后,拉取 GET 返回空 → 代码按 0 兜底,界面显示"0人已读"**,不是报错、不是"查无此数"。**消失的是"数字",不是"消息"**——消息内容永久在 MySQL,只有已读数这个瞬时字段回落。
- **为什么接受**:已读数是瞬时展示(给发送者当下看),7 天前的历史已读数没人关心;保留历史已读数需要 MySQL 持久化,而那是写放大(见下)。

### 为什么拒绝水位落 MySQL(决策记录)

**演进方向 2 曾提"水位落 MySQL 消除 TTL 过期问题",经评估不可行**:

- 每次成员已读上报都要 UPSERT 一次 MySQL(水位)+ 查询"几人读了"要扫 MySQL 水位 → **读流程碰 MySQL、写放大回到"每次读一次写"**,正是群已读要规避的
- 群聊成员数 × 消息数,MySQL 写压力远超单聊(单聊一对一、量小可落)
- 收益仅为"7 天前的历史已读数可查",而这是没人看的展示字段

**结论**:群已读保持 Redis + TTL(瞬时、内存友好、读流程不碰 MySQL),接受"7 天前已读数回落为 0"。若要"谁读了"列表或永久已读,再单独设计(演进方向)。

## 9. 发送者计数:为什么发送者必须自动计入

**实测 bug 场景**:A 发群消息后,A 的界面显示"0人已读",但 B 明明读了。

根因:A 发送时,openConversation 上报的水位是发消息**之前**的最大 seq;新消息的 seq 更高,A 的水位没覆盖自己刚发的消息 → A 不在计数里 → readCount = 仅 B(1)→ A 的界面 count-1 = 0(把唯一的读者减掉了)。

**修复**:群成员发消息落库后,自动推进发送者自己的水位(`ReadService.advanceGroupReadOnSend`):

```java
// GroupService.handleGroupMessage,落库成功后:
readService.advanceGroupReadOnSend(groupId, payload.getSenderId(), seq);
```

发送者已看到自己的消息(它在 UI 里),所以其水位覆盖自己的消息 → 计数总包含发送者 → `count-1` = 其他已读人数,语义一致。

## 10. 异常面分析(诚实,按类处理)

### A 类:正确性关键 → Lua 原子强制(不是 happy path)

| 异常 | 兜底 |
|---|---|
| 两个设备并发上报 | Lua 水位只进不退,后到忽略 |
| 乱序上报(先 50 后 30) | 同上,幂等 |
| 水位推进 + 计数 INCR 的原子性 | 合成一段 Lua,无中间态 |
| 多 chat 实例并发 | Lua 单线程串行 |

### B 类:展示偏差 → 接受自愈,不为展示增强上复杂度

| 异常 | 处理 |
|---|---|
| READ_ACK 上报丢失(网络断) | fire-and-forget,丢了该成员这次没计入;下次打开群重新上报,**最终一致** |
| Redis 重启,水位+计数全丢 | 成员重开群重新上报 → 自动重建;老消息已读数本来就该过期 |
| 水位 TTL 过期后重复计数 | 水位 TTL(30天) > 计数 TTL(7天),窗口极窄;接受轻微偏差 |
| 成员退群后计数残留 | 计数含历史成员,轻微偏差;或按当前成员过滤(查询时,不常查) |
| 实时推送丢失 | 拉取接口 readCount 兜底,重开可见 |

### C 类:客户端约束(设计要写死)

| 约束 | 说明 |
|---|---|
| **客户端必须只上报实际渲染的最大 seq** | 打开群渲染了最近 100 条 → 上报可见最大 seq;报 serverMaxSeq 会把没显示的老消息虚高算已读 |

### D 类:明确不做

- 已读上报的重传/ACK(展示增强,丢了自愈)
- 群已读落 MySQL(瞬时数据)
- 群已读群广播(写放大,方案选择)
- 精确"谁读了"列表(需要时按成员水位筛)

**面试讲法**:异常分三类——① 并发/乱序/多实例/原子性这类正确性关键用 Lua 钉死;② Redis 重启/上报丢失/水位过期这类展示偏差接受自愈或轻微偏差(已读是展示增强不是可靠性锚点);③ 客户端必须只上报实际渲染的 seq(设计约束)。不为展示增强上消息级的可靠性机制。

## 11. 边界情况

| 场景 | 处理 |
|---|---|
| 发送者自己算不算 | 计数含所有成员(发送者自动计入),界面 count-1 显示"其他已读人数" |
| 离线成员 | 不上报不计入;上线打开群上报后补上 |
| 新成员入群 | 水位从 0 开始,上报可见范围(尾部),只计入实际看过的 |
| 多设备 | 水位用户级(同单聊),手机读的电脑也算 |
| 计数 key 无限增长 | TTL 7 天自动消失 |
| 大群 | 本方案面向小群(≤200);大群计数读放大,演进方向见第 15 节 |
| 非成员上报 | isMember 校验拒绝,不计数 |

## 12. 实际改动清单(逐文件)

**协议层(im-common)**
- `DownstreamEnvelope` 加 `TYPE_GROUP_READ`(实时推送给发送者)

**连接层(im-connect)**
- `DownstreamConsumer` 映射 `TYPE_GROUP_READ` → MSG_ACK 帧

**业务层(im-chat)**
- `ReadService`:`handleReadReport` 按 `g_` 前缀分流;`handleGroupReadReport`(isMember 校验 + Lua + notifyAffectedSenders);`advanceGroupReadOnSend`(发送者自动计数);`GROUP_READ_LUA`(返回旧水位)
- `GroupMessageItemDto` 加 `readCount` 字段
- `GroupService.pullGroupMessages`:`multiGet` 批量取整页计数挂到每条消息;`handleGroupMessage` 落库后调 `advanceGroupReadOnSend`
- `GroupService.joinByCode`:`createGroup` 加指定 id 重载,用 Lua 返回的 groupId 落库(修复面对面建群列表查不到)

**客户端(clients)**
- `client-core.js`:`_onAck` 识别 `{conversationId, seq, readCount}` → `onGroupRead` 回调
- `main.js` / `preload.js`:透传 `msg:group-read`
- `renderer.js`:放开群聊 reportRead(打开群/收消息);群消息渲染"n人已读"(自己发的 count-1);`onGroupRead` 实时更新已读数
- `styles.css`:`.msg-read` 样式

## 14. 面试讲法(一段话)

> 群聊已读难点在**读扩散只有一份消息,没有"每接收者一份"挂已读状态**。我的模型是"成员水位 + 预聚合计数":每个成员维护群内已读水位(和单聊同构),上报时水位原子推进、对区间内每条消息 INCR 计数——批量读只做一批原子 INCR,写放大从"人×消息"降到"视口大小",查询 O(1)。实时性上群聊**不群广播**(每个成员读一下推全群是写放大),改成:发送者自动计入自己的水位 + **只推给受影响消息的发送者**(区间 ≤ 20 条),其他场景按需查(拉取接口每条带 readCount)。协议零改动(复用 READ_ACK),存储只放 Redis + TTL(瞬时数据,丢了成员重开群自愈)。异常分三类:并发/乱序/原子用 Lua 钉死,Redis 重启/上报丢失接受自愈,客户端只上报实际渲染的 seq。

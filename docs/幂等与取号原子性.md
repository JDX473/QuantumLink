# IM 幂等与取号:并发下的原子性

> 自研 IM(QuantumLink)并发正确性实录:为什么"幂等判断 + 分配 seq"不会放重复消息进队
> 技术栈:Java 17 · Netty · RocketMQ · Redis · MySQL
> 场景:客户端重传 / 多端并发 / 多 chat 实例下,同一条消息只被处理一次

---

## 一、序言:可靠投递与有序的交汇点

IM 的核心诉求是**不丢、不重、不乱序**。"不重"(幂等去重)和"不乱序"(有序)在业务层有一个交汇点——`MessageService.handleUpstream` 的**保序段**里,连着做两件事:

```
保序段(Orderly 消费,按会话串行)
  ① 幂等判断  → SETNX 写 dedup 键
  ② 分配 seq  → Redis INCR 取号
```

面试时这里必被追问一个问题:**"幂等判断和分配 seq 是原子操作吗?假设两个一样的消息并发,都通过了幂等判断,不就重复发两次了吗?"**

这个问题问的是并发正确性的核心——不是"结果对不对",而是"**为什么在并发下不会错**"。本文把答案拆到最底层。

---

## 二、问题提出:TOCTOU 竞态

### 场景

A、B 是**两条完全相同的消息**(同一个 `sender_id` + `client_msg_id`,即同一条消息的两次投递/重传),都还没被处理。

### 担心的流程

如果幂等判断是"**先查后写**":

```java
// 危险版本:先 GET 查,再 SET 写 —— 有竞态!
if (!redisTemplate.hasKey(dedupKey)) {   // ① 检查:不存在
    redisTemplate.opsForValue().set(dedupKey, "1");   // ② 写
    ... 取 seq ... 落库 ...
}
```

并发下这是典型的 **TOCTOU(Time-Of-Check-To-Time-Of-Use)**:

```
A: ① hasKey(key) → 不存在
   ← A 在这里被抢占(Redis 命令之间,A 的线程被换下)
B: ① hasKey(key) → 也不存在   ← 两个都"检查通过"!
A: ② set(key)               ← 两个都写入
B: ② set(key)
→ 两条都去取 seq、都落库 → 重复消息发了两次
```

**这个竞态是真实的**——只要幂等判断是"检查"和"写入"两条独立命令,中间就有这个窗口。

---

## 三、关键答案:幂等判断用 SETNX,一步原子,没有"检查"这一步

看真实代码(`MessageService.java:91`):

```java
Boolean first = redisTemplate.opsForValue()
        .setIfAbsent(dedupKey, "1", DEDUP_TTL_SECONDS, TimeUnit.SECONDS);
```

`setIfAbsent` = **SETNX(set-if-not-exists)**,一条 Redis 命令,**"检查"和"写入"合并成一个原子动作**——Redis 内部先判断 key 是否存在、不存在才写入,整个过程不存在中间态。

所以 A、B 无论以什么顺序执行:

```
A: SETNX(key) → key 不存在 → 写入成功 → 返回 true  → 走取号
B: SETNX(key) → key 已存在 → 写入失败 → 返回 false → 走去重
```

两个 SETNX **必然只有一个返回 true**,不存在"两个都过"。这正是文档里"幂等双保险"的第一层:**SETNX 把 check 和 set 合并成一步,从根上消灭 TOCTOU**。

> 补充:即便 A、B 不在同一个消费线程(极端情况),Redis 是**单线程串行执行命令**的,两条并发 SETNX 也会被 Redis 内部串行化——先到先赢。SETNX 的原子性**不依赖**消费方怎么调度。

---

## 四、那"幂等 + 取号"整体呢?不是 Redis 事务,靠串行消费

第二个问题:"SETNX 和 INCR 是两条命令,能保证一个完整动作吗?"

**答案:不是 Redis 层的事务(MULTI/EXEC/Lua),但逻辑上是原子的——靠的是 Orderly 串行消费。**

`handleUpstream` 跑在 `MessageListenerOrderly` 的单线程里(`UpstreamConsumer.java:53`)。A、B 是同一会话(同一 conversationId)→ 同一 MQ 队列 → **同一个消费线程**:

```
消费线程:  A 的 SETNX → INCR → submit  → 完整执行完
           B 才进来 → SETNX 必然撞上已存在的 key → 走去重
```

所以"SETNX→INCR"虽然两条命令,但在一个线程里**顺序执行、不会被同会话的另一条消息插进来**。多 chat 实例也一样——同 group 里一个队列同一时刻只被一个实例持有(RocketMQ 队列锁 + broker LOCK_BATCH),仍是一条线程。

**关键区分(面试值得讲清):**
- SETNX 单条命令的原子性 = **Redis 命令原子性**(单线程执行);
- SETNX→INCR 整体的原子性 = **串行消费保证**(单线程内顺序执行),不是 Redis 事务。

## 五、三层保险:重复消息最终只落库一次

| 层 | 机制 | 挡住什么 |
|----|------|---------|
| ① | SETNX 原子命令(`MessageService.java:91`) | 并发双写的 TOCTOU(两个都"检查通过") |
| ② | Orderly 单线程串行消费(`UpstreamConsumer.java:53`) | SETNX→INCR 整段不被同会话消息打断 |
| ③ | DB 唯一索引 `uk_sender_clientmsg(sender_id, client_msg_id)`(`schema.sql:62`) | Redis 丢失 / dedup 键过期后的重传 |

第③层挡住的具体场景(`MessageService.java:129-138`):假设 Redis 的 dedup 键过期(或 Redis 重启清零)后,客户端用**同一 client_msg_id** 重传——此时 SETNX 又能成功、又会取一个新 seq,但落库时:

```java
try {
    messageMapper.insert(message);
} catch (DuplicateKeyException e) {
    // DB 唯一索引兜底:SETNX 都过但 insert 撞唯一键 → 视为重复
    Message existing = findByIdempotencyKey(...);
    if (existing != null) sendStoreAck(payload, existing.getId(), existing.getSeq());
    return;
}
```

DB 唯一索引**永远**判得出重复——哪怕 Redis 整个丢了。这就是"双保险"的意义:Redis 挡 99.9%,DB 是最后一道永远在的墙。

## 六、边界分析(诚实盘点)

### 边界一:async 窗口——B 的 `findByIdempotencyKey` 可能查不到(无害)

单聊是两段式:SETNX 成功后的**落库在 `asyncProcess` 线程池**(`MessageService.java:108`),不在 Orderly 线程。若 B 紧跟着 A 进来,SETNX 撞 key 失败,但 A 的行**可能还没插入 DB** → `findByIdempotencyKey` 返回 null(`:95`)→ B 静默丢弃、不回 ACK。

- **不重复**:A 一定会落库、并回 ACK(ACk由A发),消息只存一份;
- **无害**:只是 B 路径不回 ACK,发送方不会收到重复消息;
- 要知道这个窗口存在——它是两段式"取号与落库分离"的自然产物。

### 边界二:落库失败但 SETNX 已写 → 重传被挡 7 天(真实缺口)

这是**唯一的实质缺口**:

```
A: SETNX 成功 → 取 seq → asyncProcess insert 失败(DB 抖动等非重复原因)
   → 外层 catch(MessageService.java:155)只 log.error,消息没落库
   → 但 dedup key 已经写进去了(TTL = 7 天,MessageService.java:65)
客户端同 UUID 重传 → SETNX 撞 key → findByIdempotencyKey 返回 null
   → 消息被静默丢弃,7 天内无法恢复
```

**性质**:概率低(DB insert 失败本身是异常),但一旦发生就是"静默丢消息",且被 dedup 键挡住重试。**修复方向**:
1. insert 失败时 `DEL` 掉 dedup key(让重传能重新走一次);或
2. dedup 键 TTL 缩短、把 DB 唯一索引当主判据;或
3. 把"取号+落库"放进同一事务边界(改动大,破坏两段式并发)。

当前设计选择接受它(DB 挂了大局已坏),但面试被问"幂等键会不会误伤重传"时,要能讲出这个边界和修复方向。

### 群聊路径没有 async 窗口

群消息(`conversationId` 以 `g_` 开头)走 `GroupService.handleGroupMessage`(`MessageService.java:80` 同步调用),**SETNX→INCR→insert 全在 Orderly 线程内完成**(`GroupService.java:238-261`),**没有 async 窗口**——群路径连边界一都不存在。代价是 Orderly 线程内做的事变多,单条慢消息阻塞队列更久(吞吐 vs 正确性的又一个取舍)。

### 重复 ACK 是幂等的

A 走正常路径回一次 ACK-STORE;若 B 走去重路径且查到了原行,也会 `sendStoreAck` 再回一次。**同一 clientMsgId 收到两个 STORE ACK 没问题**——客户端按 `clientMsgId` 精确匹配(`client-core.js`),第二次是 no-op,状态只进不退。

## 七、面试问答(建议背熟)

**Q1: 幂等判断和分配 seq 是一个原子操作吗?**
> 分两层。SETNX 单条命令是原子的(Redis 单线程执行,"检查+写入"一步完成,没有 TOCTOU 窗口)。SETNX→INCR 作为整体不是 Redis 事务,但靠 Orderly 单线程串行消费保证——同会话同队列同线程,一条消息的 SETNX→INCR 完整执行完才处理下一条,逻辑上原子。

**Q2: 两个一样的消息并发,会不会都通过幂等判断、重复发两次?**
> 不会。幂等判断用 `setIfAbsent`(SETNX),检查与写入是同一个原子命令,不存在"检查完还没写入"的中间态。两个并发 SETNX 在 Redis 里串行执行,必然只有一个成功、另一个撞 key 走去重。重复消息最终只落库一次。

**Q3: SETNX 和 INCR 不是一条命令,怎么保证整体不错?**
> 靠串行消费,不靠 Redis 事务。A、B 同会话 → 同队列 → Orderly 单线程,一个处理完才处理下一个,所以 B 的 SETNX 一定撞上 A 已写入的 key。多实例下同队列同一时刻只被一个实例持有(队列锁 + LOCK_BATCH),仍是单线程。

**Q4: 多 chat 实例下幂等还安全吗?**
> 安全。① SETNX 的 key 是全局共享的,谁先 SETNX 谁赢,与实例无关;② 同会话的队列被同一 group 只分配给一个实例消费,不会两个实例同时处理同一条消息;③ 即便极端情况(如 Redis 键过期后重传)让两条都过了 SETNX,DB 唯一索引 `uk_sender_clientmsg` 兜底——insert 撞键即判重,回原 seq 的 ACK。

**Q5: DB 唯一索引和 SETNX 功能重复吗?**
> 不重复,是两层防线。SETNX 是快速去重(挡 99.9%,亚毫秒,防并发 TOCTOU);DB 唯一索引是最终兜底(Redis 丢了、键过期、或任何绕过 SETNX 的重复都能判出)。前者挡"当前并发",后者挡"历史残留"。

**Q6: 幂等键会不会误伤重传?**
> 正常重传不会被误伤——重传带同一 `client_msg_id`,SETNX 撞 key 走重复路径,`findByIdempotencyKey` 查原行、回原 seq 的 ACK,消息不重复落库。但有一个真实边界:如果首次落库因非重复原因失败(DB 抖动),SETNX 键已写、TTL 7 天,此时重传会被静默丢弃。修复方向:insert 失败回滚 dedup 键,或缩短 TTL 让 DB 唯一索引做主判据。

**Q7: 单聊和群聊的幂等路径有什么不同?**
> 机制同构(都是 SETNX→INCR→insert + DB 唯一索引),区别在**是否异步**:单聊是两段式,落库在 `asyncProcess` 线程池,存在"B 查原行可能查到 null"的 async 窗口(无害);群聊 `handleGroupMessage` 全同步在 Orderly 线程完成,没有这个窗口,代价是单条慢消息阻塞队列更久。

## 八、经验总结

1. **"先查后写"必死,"查写一体"才安全**。任何"检查状态再写入"的逻辑,在并发下都有 TOCTOU,必须用原子命令(Redis SETNX)或乐观锁/版本号把 check 和 set 合并。

2. **分布式正确性靠"串行 + 原子 + 兜底"三层,缺一不可**。SETNX 管并发原子性,Orderly 管流程串行性,DB 唯一索引管最终一致性。任何一层单独都不够——但三层叠起来,重复消息在任何时序下都只落库一次。

3. **"原子"有两种:命令原子和流程原子**。Redis 单线程给的是命令原子(SETNX 单命令);流程原子(SETNX→INCR 整段)靠串行消费,不是靠事务。面试时要能区分这两种原子性,才能回答"这两条命令怎么保证不错"。

4. **两段式(取号与落库分离)会留下 async 窗口,群聊同步路径没有**——吞吐和窗口是同一枚硬币的两面,选哪边取决于你在哪一段要更强的一致性。

5. **幂等键 TTL 是双刃剑**。太长挡重传(insert 失败后 7 天内无法恢复),太短挡不住键过期后的重复。缓解:落库失败回滚键,或让 DB 唯一索引当主判据、Redis 只做快速通道。

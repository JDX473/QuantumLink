# 与真实 IM 的对比:核心同构 + 规模工程差距

> 一句话结论:**骨架和真实 IM 同构**(可靠性/有序性/接入层扩展/离线同步都做对了),差异集中在**规模工程**——存储分片、大群扩散、离线推送、监控告警,以及**架构形态**(全链路 MQ vs 关键路径 RPC)。面试的加分点不是"我做到了生产级",而是"我知道核心机制怎么做,也清楚生产还差什么、怎么演进"。

---

## 1. 与真实 IM 一致的部分(核心机制同构)

| 维度 | 本项目 | 真实 IM 的做法 | 结论 |
|---|---|---|---|
| 分层 | 接入层(connect)+ 业务层(chat),零代码依赖,独立扩缩 | 接入网关 + 逻辑层,独立部署 | ✅ 同构 |
| 会话路由 | Redis 会话表 + MQ tag 精准投递 | 路由表/路由服务,定位目标节点 | ✅ 同构(思路) |
| 负载均衡 | 最少连接 + Nacos 服务发现 | 网关负载均衡 + 注册中心 | ✅ 同构 |
| 可靠性 | 双 ACK + 客户端重传 + 幂等去重 | 全链路确认 + 重传 + 消息状态机 | ✅ 同构 |
| 离线同步 | 按 seq 游标增量拉取(afterSeq) | 客户端维护位点,增量同步 | ✅ 同构 |
| 已读回执 | 对端水位推导,不写共享消息行 | 已读位点/已读回执 | ✅ 同构 |
| 多端 | deviceId + 多端全推 | 多端同步 | ✅ 同构 |
| ID | 雪花 + serverMsgId String 下发(JS 精度) | 长 id 下发转字符串是通用坑 | ✅ 同构 |

**这几条证明核心问题(消息不丢、顺序、扩容、离线)都做对了**,是项目最值钱的部分。

## 2. 与真实 IM 的差异(诚实列出)

### 差异 1:架构形态——全链路 MQ vs 关键路径 RPC

```
本项目: client → connect →【MQ】→ chat → 存储 →【MQ】→ connect → client
生产:    client → 接入网关 →【RPC】→ 消息服务 → 存储 →【MQ/推送通道】→ client
```

- **本项目**:上行(connect→chat)和下行(chat→connect)**全部走 MQ**。换来零 RPC 基础设施、天然解耦;代价是每跳多一次 MQ 延迟、把有序性押在 MQ 的 orderly 消费上。
- **生产 IM**:发消息关键路径多用 RPC(gRPC/Dubbo)——请求-应答、低延迟;MQ 只用在**扇出/推送**这种单向异步场景。
- **对本项目的意义**:MVP 全 MQ 完全合理(能讲清"为什么"——两段式 + 队列 hash 保序);生产关键路径换 RPC 降延迟。面试要能接住"为什么不直接 RPC",答案见 `docs/MQ与RPC选型.md`。

### 差异 2:存储量级——单 MySQL 无分片 vs 海量分片

- **本项目**:一个 MySQL,消息表单表。
- **生产 IM**:消息表按**用户维度分库分表**(亿级用户)、按会话/群分片,单库单表放不下。
- **本项目预留**:群表独立(可独立分片)、`conversation_id`/`group_id` 可作为分片键,但分片逻辑未实现。

### 差异 3:群扩散模型——纯读扩散 vs 读写扩散混合

- **本项目**:纯读扩散(群消息落一份,成员各自拉取)+ 在线按节点聚合推送。
- **生产 IM**:小群读扩散,**大群写扩散**(每条消息写进每个成员收件箱)或混合——大群读扩散的"每成员已读位点 + 拉取"开销太大。
- **本项目取舍正确**(小群读扩散);面试讲清"为什么大群要换写扩散"就完整,见 `docs/群聊设计.md`。

### 差异 4:有序性——全局会话有序 vs 单发送者有序

- **本项目**:**全局会话有序**(A#B 会话内所有消息严格按发送顺序,seq 单调)。
- **微信**:**单发送者有序 + 时间戳展示**(同会话不同发送者的消息可交织,客户端按时间排)。
- **取舍**:本项目的保证更严格,代价是"单会话一个串行取号点"(热会话瓶颈);微信用更弱保证换掉瓶颈。**"更正确 vs 更可扩展"的经典取舍,面试讲清选了哪边、为什么就是加分。**

### 差异 5:功能面——生产 IM 有、本项目没做的

| 生产 IM | 本项目 |
|---|---|
| **离线推送**(APNs/FCM/厂商通道,App 后台也收到通知) | 离线 = 重连后拉取,无系统推送 |
| **在线状态服务**(presence) | 只有"连接在线",无状态服务 |
| 消息撤回/编辑/回滚 | 无 |
| 好友关系/复杂群管理 | 只有基础群 |
| 监控告警/全链路 trace | 只有日志 |

## 3. 演进路线图(按价值排序)

```
现在(核心链路完成,MVP 量级)
  │
  ├─ 工程加固:seq 发号回填原子化 / 客户端重连重调度 / 优雅缩容
  │
  ├─ 规模演进:关键路径 RPC 化、存储分库分表、大群写扩散
  │
  └─ 产品面:离线推送、在线状态、消息撤回、监控告警
```

## 4. 面试怎么讲(关键)

**别吹"和微信一样"。** 正确姿势是分层说:

> "我实现的是一套真实 IM 的核心链路:接入/业务分层、会话路由、双 ACK + 重传 + 幂等、按 seq 增量拉取、已读水位、多端同步——这些和主流 IM 是一个思路。但生产 IM 是另一个量级的工程,我知道差距在哪:① 存储要按用户/群分库分表(我留了分片键但没做);② 大群要读写扩散混合;③ 要有离线推送和在线状态服务;④ 关键路径生产会用 RPC 而不是全 MQ。我的演进方向就是补齐这些。"

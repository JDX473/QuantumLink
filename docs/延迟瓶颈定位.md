# 延迟瓶颈定位:MySQL 双 fsync 是 P50/P99 的根因

> 压测报告 3/4 遗留问题:P50 70-195ms、P99 174-5819ms 不好看,瓶颈到底在哪?
> 本文是专项定位的完整记录:消费链逐段埋点 → 单变量隔离实验 → 因果链证实 → 边界与优化方向。
> 日期:2026-08-14。环境:腾讯云 8C16G,chat×2(8081/8082)+ connect×2(19001/19002)全同机。

## 一、结论先行

| 结论 | 证据 |
|---|---|
| **根因 = MySQL 双 fsync**(`innodb_flush_log_at_trx_commit=1` + `sync_binlog=1` + `flush_method=fsync`) | 隔离实验(唯一变量=flush 配置):insert p50 **10.8→2.7ms**(-75%),客户端 P50 198→99ms、P99 **5819→381ms**(-93%),积压消失 |
| **放大器 = 无界线程池队列** | 饱和时 async_wait p50 **822ms**、p99 4442ms——`Executors.newFixedThreadPool` 的 LinkedBlockingQueue 无界,超载只堆不拒 |
| **800/s 硬拐点 = fsync 服务时间钉死的容量边界** | 10.8ms/条 × 16 线程(2 实例×8)≈ 1480/s 理论,重尾+排队把实际容量压到 ~800/s;flush=2 后 2.7×16≈5926/s,800/s 无拐点 |
| **保序不是延迟主体** | 保序段(SETNX+INCR)实测 **p50 1.5ms**;它的代价是吞吐上限(8 路并行)+ 队列连坐,不是每条消息的延迟 |
| **P50 物理下界 ≈ 52ms**(flush=2 实测) | 固定段 33ms(其中 **mq_wakeup 20ms 是最大单项**,RocketMQ 拉取唤醒)+ 排队 ~19ms |

## 二、方法:消费链逐段埋点 + 单变量隔离实验

### 2.1 PerfStats 埋点(新增 `im-chat/.../util/PerfStats.java`)

消费链拆成 8 段,每段一个环形缓冲(65536 样本)+ 后台线程每 5s 打 `PERF|stage:p50/p90/p99/max` 到 stdout(即 nohup 日志),**零客户端改动**:

```
客户端 send ──cli_to_broker──▶ connect produce ──mq_broker──▶ broker 落盘 ──mq_wakeup──▶ chat 消费
(带 clientTime)              (bornTimestamp)                (storeTimestamp)   Orderly:
                                                                               ┌─ setnx(幂等)
                                                                               └─ incr(取号)  = orderly_total
                                                                               ↓ submit
                                                                  [asyncExecutor 队列] async_wait
                                                                  ├─ insert(MySQL 落库)
                                                                  ├─ ack_send(回 ACK-STORE)
                                                                  └─ push_send(下行推送) = async_total
```

时间戳来源:`bornTimestamp`(connect 生产时钟,同机同源)、`storeTimestamp`(broker 落盘)、`clientTime`(客户端,MessagePayload 原样带下去)。系统属性 `im.perf.stats.enabled=false` 可关,生产可保留(单次 record ≈ 纳秒级)。

### 2.2 隔离实验(唯一变量)

同负载(800/s 阶梯、同参数、同预热轮)下只改 MySQL 两个参数:

- 实验组:`SET GLOBAL innodb_flush_log_at_trx_commit=2; SET GLOBAL sync_binlog=0;`
- 对照组:默认 1+1(即线上/压测原状态)
- 实验后**已恢复 1+1**,库不留实验状态

## 三、根因:MySQL 双 fsync

### 3.1 隔离实验数据

| 指标 | flush=1 + sync_binlog=1(原配置) | flush=2 + sync_binlog=0(实验) | 变化 |
|---|---|---|---|
| insert(单条落库)p50 | **10.8ms** | **2.7ms** | -75% |
| 客户端 P50(发→ACK-STORE,800/s) | 198ms | 99ms | -50% |
| 客户端 P99(800/s) | **5819ms** | **381ms** | -93% |
| async_wait(线程池排队)p50 | **822ms** | 27.6ms(500/s 档) | 积压消失 |
| mq_up p90(上行 MQ 投递) | 2084ms | 47ms | 积压消失 |

500/s 档同趋势:flush=1+1 时 P50 71ms/P99 ~180ms;flush=2 时 **P50 52ms/P99 133ms**。

### 3.2 因果链

```
双 fsync(redo 每次落盘 + binlog 每次落盘,云盘 fsync 抖动大)
  → insert 服务时间 10.8ms(每条消息都吃满)
  → 16 线程(2 实例 × 8)理论容量 1480/s,重尾拖到实际 ~800/s
  → 到达率 > 容量 → asyncExecutor 无界队列堆积(只堆不拒,async_wait p50 822ms)
  → 客户端 P50 被排队抬高、P99 断崖(5819ms)
```

**为什么 P50 也被抬高(不只是 P99)**:fsync 是每条消息的固定成本(10.8ms 进 P50 分母)+ 饱和后排队时间也进 P50(822ms 的排队压过半数样本)。

### 3.3 800/s 硬拐点的完整解释

报告 3/4 测到"健康 600/s、拐点 600-800、硬拐点 800/s 断崖",当时只知现象不知机制。现在闭环:

1. **容量钉死**:insert 服务时间(10.8ms)× 线程数(16)= 吞吐上限——这就是为什么 800/s 是"硬"拐点,不是渐变;
2. **翻转机制**:到达率一过容量,无界队列开始只进不出,排队时间指数放大(async_wait 822ms),客户端延迟断崖;
3. **不丢消息的原因**:Orderly 消费 + MQ 本身有界(消费位点不提交),积压堆在 MQ 和线程池队列里,没有静默丢弃——延迟爆炸但数据完整(报告 4 的"崩溃区 0 丢失"与此吻合);
4. **flush=2 验证**:insert 2.7ms → 理论容量 5926/s → 800/s 时队列不进积压区 → P99 381ms 平缓无断崖。容量边界确实是 fsync 钉的,不是保序钉的。

## 四、健康区 500/s 全链分解(52ms 花在哪)

flush=2 下 500/s 一轮(样本 44895)的完整拆账:

| 阶段 | p50 | 说明 |
|---|---|---|
| cli_to_broker | 3.0ms | 客户端→connect→MQ 落盘 |
| mq_broker | 1.0ms | produce→broker 追加(快,非瓶颈) |
| **mq_wakeup** | **20ms**(p90 57) | **broker→consumer 拉取唤醒,最大单项** |
| orderly_total(SETNX+INCR) | 1.5ms | 保序段,极快 |
| async_wait(线程池排队) | ~19ms 稳态(埋点上界 27.6,环形缓冲含预热样本) | 排队 |
| insert | 2.6ms | flush=2 后 |
| ack_send | 5.0ms | 同步 MQ produce 回执 |

固定段合计 33ms + 排队 ≈ 52ms = 客户端实测 P50 52ms ✓(端到端 58ms = ACK 52 + 下行推送 ~6ms)。

**mq_wakeup 20ms 是什么**:storeTimestamp(broker 落盘)→ chat 消费之间的固定延迟,即 RocketMQ push consumer 的"长轮询唤醒 → 拉取 → 消费线程拾取"链路。P50 就 20ms 说明是每条消息都吃的固定成本(候选机制:broker 长轮询 hold 请求的唤醒路径、PullMessageService 单线程调度),是除 fsync 外第二大优化项,机制值得深挖(见 §7)。

## 五、保序的真相(回答"是不是保序导致 P99 高")

**不是。** 实测数据钉死这个结论:

- 保序段(SETNX + INCR)整个只有 **1.5ms**,进 P50 分母都排不上号;
- P50 的主体是 fsync(10.8→2.7ms 的隔离实验直接把 P50 砍半)+ MQ 双跳(20ms)+ 排队;
- **保序的真正代价是另外两项**:
  1. **吞吐上限**:Orderly 按队列串行,4 队列 × 2 实例 = 8 路并行——并发度上限,800/s 硬拐点的"并行路数"部分;
  2. **连坐放大**:同一队列里一条慢消息(如 fsync 抖动)阻塞队列上所有后续消息,尾部被串行放大。

面试讲法:**"保序用 1.5ms 的串行段换正确性,代价不在单条延迟,在并行度上限和队列连坐;P50/P99 的主犯是存储持久化策略,与保序正交。"**

## 六、P50/P99 边界总结(用户问题的直接回答)

| 边界 | 数值 | 含义 |
|---|---|---|
| P50 下界(当前架构) | ≈52ms(flush=2) | 固定段 33ms + 稳态排队;想再降必须先动 mq_wakeup 20ms |
| P50 上界(健康) | <100ms | 保持到达率 < 容量 × 0.7 左右 |
| 健康区 / 拐点 / 硬拐点(flush=1+1) | <600 / 600-800 / **800/s** | 硬拐点 = fsync 容量边界,参数化的,不是架构常数 |
| 硬拐点(flush=2) | >800/s(未触顶) | 容量上移到 ~5900/s 理论,受其他瓶颈限制(未测) |
| P99 健康 / 崩溃区(flush=1+1) | ≤212ms / 5819ms | 崩溃区=排队,不是故障(0 丢失) |
| P99(flush=2,500/s) | 133ms | 尾部来源:mq_wakeup 重尾 + async_wait 重尾 |

## 七、优化方向与优先级

| 优先级 | 项 | 预期收益 | 方案 |
|---|---|---|---|
| 🔴 已证 | MySQL flush 调优 | **P50 -50%,P99 -90%,容量 ×2+** | flush=2(+ sync_binlog=1 折中),见 §8 权衡 |

## 八、生产配置决策点(给未来压测/部署)

**现状已恢复 1+1(默认,最安全)。** 两个选项的数据支撑:

- **flush=1 + sync_binlog=1(当前)**:崩溃丢 0 事务;代价 = P50 70-198ms、容量 800/s。适合"面试项目强调正确性、流量小"。
- **flush=2 + sync_binlog=1(生产 IM 常见折中)**:崩溃丢 ≤1s redo(已 commit 未刷),binlog 不丢(备份/主从完整);P50 -50%、容量 ×2+。消息在 MQ 里还有副本(重放可补),IM 场景数据不丢(丢的是"这 1s 内已确认但没进 binlog 的事务"——严格讲要提示发送方重发,当前实现没做,是已知取舍)。

**建议**:本项目保持 1+1,把 800/s 写为"已知容量边界"和面试答案——"我知道它由 fsync 钉死、知道怎么改、为什么没改"。压测时如需更高容量,临时 SET GLOBAL 即可(重启 MySQL 失效,天然不会忘记还原)。

## 九、方法学与遗留

- **埋点污染**:环形缓冲含预热/backlog 样本,跨轮读 p50 会被历史污染(本轮 async_wait p50 27.6 即上界,稳态 <27)——读数据前先看 cnt 与轮次对应,或单轮重跑;
- **隔离实验纪律**:唯一变量、同负载同预热、实验后恢复配置(本次已恢复 1+1);
- **遗留(未做)**:mq_wakeup 20ms 的机制深挖(broker 侧长轮询唤醒/消费端拉取调度,需 broker 日志/抓包);flush=2 下的新容量上限(理论 5900/s,其他瓶颈未知);有界队列背压改造(涉及消费失败语义,需设计)。

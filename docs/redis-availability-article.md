# Redis 挂了怎么办:QuantumLink 的 Redis 依赖审计与容灾方案

> 一句话结论:**当前系统 Redis 挂了,在线功能(发消息、实时收)会瘫痪,但消息一条不丢**(消息正文在 MySQL,客户端拉取兜底);要根治,得把 Redis 从"写路径和推送路径的单点"改造成"可降级的加速层"。

---

## 1. 先审计:系统到底依赖 Redis 的什么

"重度依赖 Redis"是个笼统的判断,必须拆开看。全项目 Redis key 盘点:

| Redis key | 用途 | 挂了影响 | 依赖强度 |
|---|---|---|---|
| `im:conv:seq:{conv}` / `im:group_seq:{gid}` | **seq 发号器**(INCR 取新号) | 新消息无法取号 → **写路径瘫痪** | 🔴 硬依赖 |
| `im:session:{uid}:{dev}` / `im:devices:{uid}` | **会话路由表**(谁在哪个节点) | 下行推不出去 → **实时推送全断** | 🔴 硬依赖(实时性) |
| `im:msg:dedup:{sender}:{cmid}` | 幂等去重(SETNX) | 判重失效 → **DB 唯一索引兜底**,仍可用 | 🟡 弱依赖(有兜底) |
| `im:node:conns:{nodeId}` | 连接数心跳(负载指标) | 最少连接失效 → 退化为随机/默认节点 | 🟡 弱依赖 |
| `im:read:{conv}:{reader}` | 已读水位(实时) | 已读显示不了 → **读 MySQL im_read_pos 兜底** | 🟡 弱依赖 |
| `im:user:{uid}` | 用户资料缓存 | 资料拉不到 → **直接查 DB** | 🟡 弱依赖 |
| `im:f2f:{code}` | 面对面建群时间窗口 | 该功能不可用 | 🟢 功能降级 |
| **消息正文(im_message)** | 可靠锚点 | **根本不经过 Redis** | ⚪ 无依赖 |

**关键事实:消息正文不在 Redis。** Redis 里全是元数据、状态、计数器——没有任何一条消息内容。这是"数据不丢"的地基。

## 2. Redis 挂了的真实状态(现状,诚实版)

### 2.1 发消息(写路径)——瘫痪
```
A 发消息 → chat handleUpstream
  → Redis INCR 取 seq → 抛异常
  → 走 catch → 消息既不落库、也不回 ACK-STORE
  → 客户端 3s 超时重传 → 一直失败 → 界面"发送失败"
```
**新消息发不出去**,而且由于取号在落库之前(两段式),取号失败 = 落库也没发生。已落库的历史消息安全,但写入路径整个是坏的。

### 2.2 实时收(推送路径)——断,但数据不丢
```
chat 推给 B → 查会话表 im:session:{B} → 没了(Redis 挂)
  → nodeOf 返回 null → "target offline, skip push" → 不推了
```
实时推送全断,全部退化为离线场景:B 上线后增量拉取从 MySQL 补回。**实时性没了,消息不丢。**

### 2.3 其他功能——降级
- 已读:读不到水位 → 展示降级(MySQL 有兜底)
- 用户资料:缓存 miss → 查 DB(慢一点)
- 面对面建群:不可用(窗口 key 在 Redis)

### 2.4 数据安全底线:不丢
- 消息正文在 MySQL,Redis 里没有副本
- 客户端有 seq 游标 + 增量拉取,恢复后自愈
- seq 计数器丢失 → `scripts/reconcile-seq.js` 用 MySQL 最大 seq 对齐

**结论:现状 = "单点 Redis,挂了在线功能全瘫,但数据不丢"。** 面试不能吹"高可用",要诚实说这是 MVP 的取舍。

## 3. 为什么数据不丢(设计地基)

1. **先落库、后缓存**:`messageMapper.insert` 在前,ACK/推送在后——可靠锚点是 MySQL。
2. **消息只存一份**:正文在 MySQL,Redis 无副本,不存在双写一致性问题。
3. **离线拉取兜底**:推送是尽力而为,`GET /api/conversations/{conv}/messages?afterSeq=` 从 MySQL 按 seq 补拉。
4. **幂等双保险**:Redis SETNX 挡 99.9%,DB 唯一索引 `uk(sender_id, client_msg_id)` 兜底。

一句话:**可靠性锚定在"落库 + 拉取",不锚定在 Redis。**

## 4. 逐项解决办法:把 Redis 从"硬依赖"变成"可降级层"

思路:按 Redis 用途分别处理——**该独立的独立、该降级的降级、该换的换**。

### 4.1 seq 发号器(写路径硬依赖,必须可降级/可替换)

**方案 A(近期,改动小):Redis 挂时降级到 DB 发号**
`im_conversation` 表本来就有 `last_seq` 字段(schema.sql 里 `BIGINT NOT NULL DEFAULT 0 COMMENT '事务内原子自增'`)。Redis INCR 异常时,回退到:

```sql
UPDATE im_conversation SET last_seq = last_seq + 1 WHERE conversation_id = #{conv}
```

发号慢一点(DB 行锁),但不瘫。代价:和 Redis 发号切换时 seq 可能不连续(两边各自发号),需要"取 max(Redis计数, DB last_seq)+1"对齐。这是**保可用性**的降级路径。

**方案 B(演进,大厂做法):发号服务独立**
把发号从业务链路里拆出去,用**雪花算法 + 分段取号**(美团 Leaf、滴滴 Tinyid 模式):发号服务一次取一段号(如 1000 个)缓存,本地分配;Redis/DB 只做段号源的持久化。**发号彻底不依赖 Redis 在线可用性**,Redis 挂了已取的段号还能继续发。

> 面试讲法:seq 是写路径的硬依赖,我给了两级方案——近期降级 DB `last_seq+1`,演进是独立发号服务(雪花/分段),让 Redis 变成"发号的加速缓存"而非"发号的唯一来源"。

### 4.2 会话路由表(推送路径,实时性硬依赖)

**方案:中心化查表 → 广播 + 本地命中**
Redis 挂 = 会话表没了,chat 不知道 B 在哪个节点。退化为:

```
chat 推给 B → 不再查路由表
  → 把下行消息广播给 Nacos 报告的所有健康 connect 节点
  → 每个节点查自己的本地 ChannelManager(每个节点都清楚自己的连接)
  → 命中 B 的节点推送给 B
```

- **Nacos 在这里的角色**:只提供"有哪些健康节点可以广播"(它擅长的存在性),**不做路由表**(用户级注册是心跳风暴反模式)。
- **代价**:MQ 扇出从"1 条精准投递"变成"N 条广播",换可用性。
- **收益**:实时性保住,Redis 从"路由表的唯一来源"变成"有它更高效、没它靠广播兜底"。

> 面试讲法:路由从中心化查表退化成"广播 + 本地命中",用 Nacos 的节点清单做广播目标,Redis 只是路由的优化而非依赖。

### 4.3 幂等去重(已有 DB 兜底)
Redis `SETNX` 挂了,DB 唯一索引 `uk(sender_id, client_msg_id)` 照样判重(insert 撞唯一键 → 返回原消息的 seq)。**已经是双保险**,不需要额外处理。

### 4.4 已读水位 / 用户缓存(弱依赖,直接降级)
- 已读:Redis 水位 miss → 读 MySQL `im_read_pos`(持久锚点)
- 用户资料:缓存 miss → 查 DB(慢,但可用)
- 这两个本来设计就是"Redis 加速 + MySQL 兜底",挂了对核心链路无影响。

### 4.5 面对面建群 / 群功能
- 群 seq:同 4.1(Redis INCR 发号,降级/独立)
- 面对面建群:窗口 key 在 Redis,挂了这个功能暂不可用——可接受(非核心)

## 5. 大厂参考:Redis 的正确定位

| 职责 | 正确归属 | 原则 |
|---|---|---|
| 消息、关系、位点 | MySQL / 分库分表 | 持久、可靠、不能丢 |
| 发号器 | 独立发号服务(Leaf/Tinyid/雪花) | Redis 只是加速 |
| 会话路由 | 节点广播 + 本地命中 / 注册中心 | 临时状态,可重建 |
| 缓存 | Redis(可降级) | 挂了降级,不影响正确性 |

**核心原则:强一致、不能丢的东西放持久层;Redis 只承担"可降级"或"可重建"的角色。**

## 6. 面试问答

**Q: Redis 挂了会丢消息吗?**
A: 不会。消息正文只存在 MySQL,Redis 里没有消息副本。Redis 挂 = 发不出去、推不出来,但已落库的历史消息一条不少,恢复后客户端按 seq 增量拉取自愈。

**Q: 那 Redis 挂了系统还能用吗?**
A: 诚实说:不能正常用。新消息发不出去(取号失败)、实时推送全断(路由表没了)。这是 MVP 的取舍——Redis 承担了发号和路由。

**Q: 怎么让 Redis 挂了发消息也不瘫?**
A: 两条路:① 发号降级到 DB `im_conversation.last_seq`;② 发号独立成服务(雪花/分段)。让 Redis 从"发号的唯一来源"变成"可替代的加速层"。

**Q: 为什么不用 Nacos 当路由表?**
A: Nacos 是服务发现,注册单位是节点(实例);路由表是"用户连接 → 节点",颗粒度细得多。把每个用户注册成 Nacos 实例,在线用户量上来就是心跳风暴。正确做法是广播 + 本地命中,Nacos 只提供节点清单。

**Q: Redis 的正确定位?**
A: 加速层,不是存储层。消息放 MySQL(持久锚点),发号独立(或可降级),会话路由可退化为广播,缓存可降级。Redis 的角色是"让系统更快",不是"让系统正确"——正确性由 MySQL + 客户端拉取保证。

## 7. 演进路线图

```
现在(单点 Redis,MVP)
  │
  ├─ 近期:seq 发号降级 DB last_seq+1 + 已读/资料兜底 MySQL(都是改动小的)
  │
  ├─ 中期:会话路由广播兜底(Redis 挂 → Nacos 健康节点广播 + 本地命中)
  │
  └─ 演进:发号服务独立(雪花/分段)→ Redis 彻底变成可降级加速层
```

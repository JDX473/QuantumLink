# 小群群聊设计思想

> 一句话结论:**小群 = 读扩散(一份消息,成员各自拉)+ 在线按节点聚合推送(信封 targets)+ 群内按群 id 保序。** "小"是这套设计的成立前提——读扩散的代价随成员数线性涨,小群完全可忽略,大群才需要换写扩散。

---

## 一、先定假设:"小群"意味着什么

小群指**成员规模小、人数可控**(本系统面对面建群上限 200 人)。这个假设决定了整个取舍:

- 写放大要省(读扩散)
- 读时聚合的代价可忽略(成员少)
- 不需要复杂的扩散优化(大群才需要)

**"小"不是一句话带过,它是设计的成立前提。** 面试讲群聊,第一句就该点明"我按小群设计,因为……",否则面试官会拿大群的痛点打你。

## 二、核心选型:读扩散(写一次,读多次)

小群消息**只落一份**到 `im_group_message`([GroupService.handleGroupMessage](im-chat/src/main/java/com/quantumlink/im/chat/service/GroupService.java)):

```
幂等去重(SETNX im:group_msg:dedup:)
→ 群维度取 seq(Redis INCR im:group_seq:{gid})
→ 落库一份(不按成员复制)
→ 在线推送(见下)
→ 回 ACK-STORE(群消息不回 DELIVER)
```

### 为什么读扩散

| | 写扩散 | 读扩散(本项目) |
|---|---|---|
| 存储 | 每条消息写 N 份(每成员收件箱) | 每条消息写 **1 份** |
| 写放大 | 100 人群 = 100 份写 | **1 份写** |
| 读 | 读自己收件箱,O(1) | 按群 seq 位点拉取 |
| 适用 | 大群(>500 人) | **小群** |

**读扩散的本质是"写一次、读多次"**:群消息大多数人不会反复拉,写放大的节省是实打实的。成员各自维护**群内 seq 位点**,增量拉取(`GET /api/groups/{gid}/messages?afterSeq=`),和单聊**完全同构**——离线、多端、乱序兜底全部复用。

### 为什么小群成立(面试点)

> 读扩散的代价 = "每次读要扫一遍群消息 + 过滤自己位点之后",随成员数线性涨。小群(几百人)这个代价可忽略,写扩散的"每消息 N 份写 + N 份收件箱"反而不划算。微信 500 人以上才切写扩散,本质是**读写比**的取舍:小群读少写多,读扩散赢;大群读多,写扩散赢。

## 三、在线推送:信封 targets 按节点聚合

### 难点:朴素做法 MQ 扇出爆炸

群成员分散在多个 connect 节点,如果每个成员一条 MQ:100 人群 2 节点 = 100 条 MQ。

### 解法:按节点聚合,扇出 = 节点数而非成员数

```
chat 查在线成员 → 查会话表定位各自节点 → 按 nodeId 分组:
  19001 节点: [A, C, E]
  19002 节点: [B, D]
→ 每节点一条 DownstreamEnvelope{ targets:[该节点成员], tag=nodeId }
→ 各节点消费 → 遍历 targets → ChannelManager.getAll(uid) 多端全推
```

**扇出对比:100 人群 2 节点 = 2 条 MQ,而非 100 条。** 这是小群群播能撑住的关键,也是"水平扩展能力"在群聊上的实战检验。

### 为什么改信封不改消息体(分层)

| 层 | 语义 | 决策 |
|---|---|---|
| `MessagePayload.receiverId` | "消息发给哪个群"(业务语义) | 保持单值(群 id) |
| `DownstreamEnvelope.targets` | "投递到哪些连接"(投递元数据) | 扩展数组 |

**聚合是投递优化,只影响信封层**;connect 只解析顶层(投递元数据)、不懂业务内容,对 targets 是"顶层数组"零业务认知改动。

## 四、完整链路

```
A 发群消息 → connect 按群 conversationId 选队列(群内保序)
  → chat Orderly 消费 → GroupService.handleGroupMessage
  → 幂等去重 → 群维度 Redis INCR 取 seq
  → 落库 im_group_message(1 份,读扩散)
  → 查成员 → 排除发送者 → 按 nodeId 分组 → 每节点一条 targets 信封
  → 回 ACK-STORE 给 A(群消息不回 DELIVER)
  → 离线成员:上线 GET /api/groups/{gid}/messages?afterSeq= 增量拉取
```

## 五、边界处理

| 边界 | 处理 |
|---|---|
| **群内保序** | conversationId = 群 id(`g_` 开头),connect 按群 id hash 选队列 + orderly 取号 → 群内 seq 单调 |
| **发送者不给自己回推** | `memberIds.remove(senderId)`,本地已展示 |
| **多端全推** | `ChannelManager.getAll(uid)` 遍历一个用户所有设备 |
| **离线成员** | 不推,上线按群位点拉取(读扩散 + 位点天然支持) |
| **成员列表可变性** | 用可变 List(Java 17 `.toList()` 不可变,`remove` 会抛——踩过) |
| **群 seq 回绕** | 同单聊,Redis 重启回绕 → `scripts/reconcile-seq.js` 对齐 |

## 六、面试讲法(一段话)

> 小群我用**读扩散**:群消息只落一份(写放大 0),成员各自维护群内 seq 位点增量拉取,和单聊完全同构,离线/多端/乱序兜底全复用。在线推送靠**信封 targets 按节点聚合**:chat 按会话表把成员按 nodeId 分组,每节点一条 MQ(扇出 = 节点数而非成员数),connect 遍历 targets 多端全推。群内保序靠 conversationId=群 id 走同队列 orderly 取号。群消息只回 ACK-STORE 不回 DELIVER。**小群成立的前提是读扩散代价随成员数线性涨、小群可忽略;真到大群(千级以上),这个代价 + 每成员位点的开销会变瓶颈,才需要换写扩散。**

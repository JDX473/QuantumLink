# 鉴权完整篇章:从凭证到连接生命周期

> 一句话总览:**系统用"一套凭证(token)+ 两种协议共用(TCP 握手 / HTTP)+ 连接生命周期(建连→握手→保活→踢下线→吊销→清理)"鉴权。** 核心是"三个身份各司其职(userId 锚点 / deviceId 设备 / token 会话)、吊销靠删 Redis key、踢下线靠 KICK + 重连拒绝"——以及在"握手阻塞 EventLoop""纸面吊销""token 被盗"这些被逼问出的边界上,诚实承认现状并给出演进。本文从"鉴权在保护什么"讲到"面试被深挖的每一刀",完整成篇。

---

## 1. 鉴权的本质:我们在保护什么

先分清两件事(面试第一刀常在这里):

| | 认证(Authentication) | 授权(Authorization) |
|---|---|---|
| 回答 | "你是谁?" | "你能干什么?" |
| 手段 | token / 密码 | 越权校验(会话归属、群成员) |
| 本系统 | 握手验 token、HTTP 验 Bearer | AuthContext + isParticipant / isMember |

**本系统的两层**:认证解决"这条连接/这个请求是不是李四",授权解决"李四能不能动这条数据"。越权防护是独立的第二层——不能因为 token 有效就放行所有数据(拉消息要校验会话归属、群消息仅成员可拉)。

## 2. 凭证体系:三个身份,各司其职

| 凭证 | 谁生成 | 作用 |
|---|---|---|
| **userId** | 服务端(注册分配) | 用户身份锚点,不变(所有消息/会话/设备绑它) |
| **deviceId** | **客户端**首启生成持久 UUID 存本地,服务端绑定账号 | 设备身份,多端区分;重装/重登不变 |
| **token** | 服务端(登录生成) | 会话凭证,`im:token:{token} → userId`,TTL 30 天 |

**token 是"不透明随机串",不是签名 JWT**——校验 = 查 Redis 映射,不验签名、无密钥管理。

**为什么 userId 不变锚点**:username 可变(改名),消息/会话/设备必须绑不变的 userId,否则改名就乱。

## 3. 双协议鉴权:一套凭证,两个入口

| 协议 | 入口 | 校验方式 |
|---|---|---|
| **TCP 长连接**(实时收发) | 连接后**第一帧 HANDSHAKE**(body: token + deviceId) | connect 查 `im:token:{token}` → userId |
| **HTTP 接口**(拉历史/发消息/改头像等) | `Authorization: Bearer {token}` 头 | chat AuthInterceptor 查同一 key |

**同一份 token,一个来源(登录),两个消费方**——一次登录两种通道都通,吊销在一个点生效。

## 4. TCP 握手鉴权深度

### 4.1 流程

```
客户端 TCP 连上 connect 节点
  → 第一帧必须是 HANDSHAKE{token, deviceId}
  → HandshakeHandler.channelRead0:
      非 HANDSHAKE 帧 → ERROR(AUTH_REQUIRED) + 关连接   ← 第一帧强约束
      token/deviceId 缺 → ERROR(BAD_HANDSHAKE) + 关连接
      → sessionRegistry.authenticate(token) 查 Redis → userId
        userId 为空(无效 token)→ ERROR(AUTH_FAILED) + 关连接
        userId 有效 → register(userId, deviceId, nodeId)   ← 注册 Redis 会话表
                   → ChannelManager.add(本地) + ConnectionContext.bind
                   → 回 HANDSHAKE_ACK{userId}
                   → 移除 HandshakeHandler,后续帧交 MessageHandler
```

### 4.2 三个关键设计

- **鉴权在握手阶段,不是第一条业务消息**:未握手想发业务帧直接关——"先握手后收发"是状态通道的底线
- **校验 = 本地查共享 Redis**(`commands.get("im:token:"+token)`):不是验签名、不是发鉴权服务
- **握手成功才进会话表**:身份锚定(ConnectionContext 绑定 userId/deviceId),后续消息从连接上下文取身份,不再信任客户端

### 4.3 一个真 bug:握手同步阻塞 EventLoop

**握手鉴权是 EventLoop 上唯一的同步阻塞调用**——`channelRead0` 直接调 `commands.get()`,Redis 抖动会卡住整个 EventLoop 上所有连接。

```
channelRead0(EventLoop 线程)
  → authenticate → 同步 Redis GET
  → Redis 慢 → EventLoop 卡住 → 同 EventLoop 上所有用户全卡
  → 唯一兜底是 Lettuce 3s 超时,但 3 秒全节点卡顿已不可接受
```

**正解**:异步 Redis(Lettuce async)或丢线程池,让握手不阻塞 EventLoop。这是"EventLoop 只做收发"原则的漏网之鱼。

## 5. HTTP 鉴权深度

### 5.1 流程

```
HTTP 请求 → AuthInterceptor(除 register/login/avatar 外全拦)
  → 取 Authorization: Bearer {token}
  → 查 Redis im:token:{token} → userId
  → 有效 → 写入 request attribute(AuthContext.currentUserId)
  → 无效 → 401
```

### 5.2 越权防护(认证之外的授权层)

**所有业务接口从 `AuthContext.currentUserId(request)` 取当前用户,不信任 URL 参数**:

- 拉会话列表:忽略传入 userId,用上下文里的
- 拉消息:校验会话归属(A#B 参与者)
- 改头像:只能改自己
- 群消息:仅群成员可拉

**为什么**:token 有效只证明"你是李四",不证明"你该看这条数据"。越权防护是第二层,不能省。

## 6. 过期策略与长连接

**token TTL = 30 天,校验时机因协议而异**:

| 协议 | 校验时机 | 过期后果 |
|---|---|---|
| HTTP | 每个请求 | 过期立刻 401 |
| TCP | 只在握手 | 过期不影响已建立的长连接 |

**为什么 TCP 过期不影响已建连接**:连接身份在握手时已锚定(ConnectionContext 绑定),后续收发不依赖 token;token 过期只该阻止新握手,不该打断已建会话。代价:失效无法立刻吊销已建连接,靠 30 天 TTL + 重连重新校验兜底。

## 7. 吊销与踢下线(当前:纸面吊销,无 KICK)

### 7.1 现状

```
吊销 token = 删除 Redis im:token:{token}
  → 新握手:authenticate 查不到 → 拒绝 ✓
  → 已建立的长连接:不受影响(靠心跳续期,不查 token)→ 继续活着 ✗
```

**当前吊销是"纸面吊销"**——挡新握手,踢不掉已建连接。没有 KICK 通道、没有周期重新鉴权、没有"吊销 → 通知接入层踢连接"的机制。

### 7.2 要真吊销:两层配合

```
① 快路径 KICK:服务端发现 token 应吊销 → 查会话表定位节点 → 发 KICK 控制消息
   → 节点收到 → 本地 ChannelManager 找到连接 → close()
   (复用现有 MQ tag 路由,加 KICK 信封/控制 topic)
② 持久路径:吊销 = 删 token → 客户端重连握手失败 → 出局
   (节点死时也有效:连接已随节点死,KICK 到死节点无所谓,重连握手被拒才是关键)
```

**关键认知**:只关连接不够——客户端会自动重连,若 token 还有效会重新进来(白踢)。踢下线 = 关连接 + 让重连失败两个动作一起。

## 8. 连接生命周期(完整框架)

一条连接从生到死,每一步定义"正常 + 失败"行为:

```
① 建连(accept)     正常:accept → 进握手;攻击:maxConnections + 限流;节点死:连接随进程死
② 握手鉴权         异步 Redis + 第一帧强约束 + 待鉴权超时 + 待鉴权限流
③ 会话建立         注册本地 ChannelManager + Redis 会话表(TTL 30s)
④ 保活             客户端 10s PING 刷新会话;服务端 30s 读空闲关死连接
⑤ 收发             上行 per-conversation 池;下行 EventLoop + isWritable 背压 + 拉取兜底
⑥ 踢下线           快路径(KICK)+ 持久路径(吊销使重连被拒)——当前都没有
⑦ 吊销             删 token 挡新握手;踢活连接(KICK)当前缺失
⑧ 清理             断连清理本地 + 会话表;节点死靠会话 TTL 30s 自愈
```

## 9. 攻击面全景

| 攻击 | 当前状态 | 防线/演进 |
|---|---|---|
| 空连接挂数千条 | 未握手一帧即关;已握手 30s 无心跳断 | ✅ 有(握手强约束 + IdleState) |
| 假登录灌爆握手 | 同步 Redis GET 阻塞 EventLoop | ⚠️ 要改:异步 Redis + 待鉴权超时/限流 |
| token 被盗后建连接 | 纯 token,拿 token 能冒充 | ⚠️ 无解(行业常态);靠 HTTPS + 短 TTL + 设备绑定 |
| token 被盗后吊销 | 纸面吊销,已建连接不受影响 | ❌ 要补:KICK + 重连拒绝 |
| 偷 token 换设备用 | 无 deviceId 绑定校验 | ⚠️ 要补:握手校验 token↔deviceId |
| 慢客户端拖垮节点 | isWritable 背压已加 | ✅ L1;演进有界队列 + 主动断连 |
| 共用电脑多账号 | device_id 组合唯一键(user+device) | ✅ 已支持(uk_user_device) |

## 10. token 选型:纯 token vs JWT

| 维度 | 纯 token(当前) | JWT |
|---|---|---|
| 验证 | 查 Redis(有状态) | 本地验签(无状态) |
| 吊销/踢下线 | ✅ 删 key 天然支持 | ❌ 无法撤销,靠黑名单(又查 Redis) |
| Redis 依赖 | 验证就依赖 | 吊销才依赖(黑名单) |
| 数据量 | 每会话占 Redis 内存 | token 无状态,Redis 只存黑名单 |
| 伪造风险 | 不可伪造(随机串+存在性) | 可伪造(密钥泄露) |
| 声明携带 | 不能(只当钥匙) | 能(userId/角色塞 token) |

**结论**:JWT 只省"验证"那一步;IM 要吊销、踢下线、会话状态管理,纯 JWT 有"无法撤销"硬伤。**纯 token + Redis 更适合 IM**——该补的是握手异步化 + 短期 token,不是换 JWT。

## 11. 当前缺口清单 + 演进路线

| 缺口 | 说明 | 优先级 |
|---|---|---|
| 握手同步阻塞 EventLoop | authenticate 同步查 Redis | 🔴 高(真 bug) |
| 吊销不踢活连接 | 纸面吊销,无 KICK | 🔴 高(安全) |
| 无 deviceId 绑定校验 | 握手不校验 token↔deviceId | 🟡 中 |
| token 30 天偏长 | 被盗窗口大 | 🟡 中 |
| 各端未读数独立 / 踢设备 | 设备管理有列表,无踢/未读 | 🟢 低(增强) |

## 12. 面试问答(汇总)

**Q: 为什么 token 过期不影响长连接?**
A: 连接身份在握手时已锚定,后续收发不依赖 token;token 过期只该阻止新握手。代价:失效无法立刻吊销已建连接,靠 TTL + 重连兜底。

**Q: 怎么踢下线?**
A: 两层:快路径 KICK(查会话表 → 发控制消息到节点 → close)+ 持久路径(删 token 使重连被拒)。只关连接不够——客户端会自动重连,必须同时让重连失败。当前两者都没实现。

**Q: token 被盗怎么办?**
A: 纯 token 拿 token 能冒充,这是行业常态;靠"让 token 难盗"(HTTPS/短TTL/设备绑定)+"降低影响"(可吊销)兜底,不靠"识别盗用者"。当前 token 30 天偏长、设备绑定没做,是已知缺口。

**Q: 握手鉴权阻塞吗?**
A: 当前同步查 Redis 写在 EventLoop 上,Redis 抖动卡全节点——该改成异步 Redis。

**Q: 换成 JWT 就不用和 Redis 交互了?**
A: 只省验证那步;吊销/踢下线/会话状态都要 Redis(JWT 无法撤销),IM 场景纯 JWT 有硬伤。

**Q: 纯 token 有什么问题?**
A: 每次验证查 Redis、Redis 单点、无法携带声明、每会话占内存;换来天然支持吊销、不可伪造。IM 场景更合适。
